# 巡检器(vault-check)是什么

> 这个库里躺着一套自己写的"体检工具":`50-资源/工具/vault-check/`。一条命令跑完全库,告诉你哪条链接断了、哪篇笔记没人能到达、哪张 MOC 的统计数字对不上、哪篇成品知识错放进了项目层、哪个项目还没建教学工作区。
> 本文讲它**为什么存在**、**怎么用**、**内部怎么运作**,以及它**查不到什么**。
> **本文的固定写法**:每个概念按「**为解决什么痛点而生 / 一句话定义 / 大白话注解**」三段给出。
> 关联阅读:[测试夹具是什么](<测试夹具是什么.md>)、[CLI、TUI、GUI 三种界面的区别](<CLI,TUI,GUI三种界面的区别.md>)。

---

## 一句话速览

| 名称 | 一句话定义 | 为解决什么痛点而生 |
| --- | --- | --- |
| **巡检器** | 一套本地 Python 脚本,把"这个笔记库还讲不讲道理"变成 10 条可自动判定的检查 | 库长到 141 篇后,断链、孤篇、元数据漂移靠人眼必然漏;漏了也没人告诉你 |
| **检查项(A1~A11)** | 11 条独立判据,每条只看一件事,报出`文件:行号 原因` | 一个"全库体检"如果只给一句"有问题",等于没查 —— 必须能定位到行 |
| **白名单 / 豁免** | 明确写下来的"这里断了是故意的"清单 | 模板占位、语法示例、刻意留的待补坑,会被任何朴素的检查器误报成错 |
| **自检(selftest)** | 用假库验证"该报的报了、不该报的没报" | 检查器自己写错了比不写更糟:它会安静地放过真问题 |

## 一、为什么需要它

> **为解决什么痛点而生**:2026-09-22 第一次认真整理这个库时,手工统计出来的数字是 —— **断链 13 处、`related` 双链失效 29 处、孤篇 20 篇、元数据违规 25 处、markdownlint 8677 条**。这些全是"不打开每一篇、不逐个点链接就看不见"的问题。库小的时候靠记性,长到一百多篇之后,唯一可靠的办法是让机器每次都能重算一遍。

**一句话定义**:巡检器是把"库的结构约定"翻译成可执行判据的一组脚本,跑一次就重算全库的结构健康度,并以退出码表达结论。

**大白话注解**:像体检报告。它不判断你身体好不好(内容对不对、写得好不好),只量血压血糖(链接通不通、有没有人引用、元数据齐不齐),哪项超标就把那一项和数值指给你。

## 二、怎么用

### 2.1 三条常用命令

```bash
cd "F:/0-Note/50-资源/工具/vault-check"

# 全量检查(列明细:每条问题都带 文件:行号 原因)
PYTHONIOENCODING=utf-8 python -B check_vault.py

# 只看汇总(改完东西先扫一眼)
PYTHONIOENCODING=utf-8 python -B check_vault.py --quiet

# 覆盖率与条目数(改完 MOC 之后用)
PYTHONIOENCODING=utf-8 python -B check_vault.py --coverage
PYTHONIOENCODING=utf-8 python -B check_vault.py --moc-stats
```

- `PYTHONIOENCODING=utf-8` **不是可选项**:Windows 默认 GBK,输出里的中文与文件名会直接把脚本顶崩(报 `UnicodeDecodeError` / 乱码)。
- `python -B` 只是不生成 `__pycache__`,保持目录干净。
- 想要机器可读结果给别的脚本吃,加 `--json`。

### 2.2 输出怎么读

```text
[A1 断链] 2 处
   20-领域/08-外语/西班牙语/2-词汇/词族.md:327 ../../../08-外语/西班牙语/2-词汇/不规则动词.md
[A4 MOC 未覆盖] 1 处
   20-领域/03-开发工具与工作流/Git.md:0 未在任一 MOC 出现
结论:FAIL
```

- 第一行是**分类汇总**:`[检查项] 命中数`
- 下面每行是**一条问题**:`文件:行号 详情`(行号 `0` 表示"整篇级"问题,如缺 frontmatter、未登记)
- 最后一行是**结论**:全 0 就是 `PASS`

### 2.3 退出码(能接进自动化)

| 退出码 | 含义 |
| --- | --- |
| `0` | 全部检查通过(`PASS`) |
| `1` | 至少一项有问题(`FAIL`),明细已打印 |

所以它可以直接串进脚本:`check_vault.py --quiet || echo "库里还有问题"`。

### 2.4 什么时候跑

| 时机 | 理由 |
| --- | --- |
| **改完一批笔记/链接后** | 立刻知道有没有手抖断链 |
| **搬迁、改名、重排目录之后** | 这类操作最容易留下"看着对、其实解析不了"的链接 |
| **改完 MOC 之后** | A9 会核对统计块与实物是否一致 |
| **写新笔记之后** | A4/A6 会提醒你登记进 MOC、补 frontmatter |
| 提交前(理想习惯) | 它检查的都是"提交后很难再发现的静默损坏" |

## 三、它查什么:A1~A11 速查表

| 编号 | 查什么 | 判据要点 | 常见修法 |
| --- | --- | --- | --- |
| **A1** 断链 | 相对路径链接的目标是否存在 | 跳过 `http`/`#`/`mailto`;模板占位与语法示例走白名单;代码块与行内代码先被抹白再扫 | 改路径、或补建目标文件 |
| **A2** 双链失效 | `[[名]]` / `[[目录/名]]` 能否解析到真实文件 | 裸名按**文件名**命中,带路径的按**路径后缀**命中(库里有 18 个同名 `!项目说明.md`,裸名折叠会误判) | 改成正确文件名,或补路径消歧 |
| **A3** 孤篇 | 全库没有任何入链的笔记 | 裸双链只在**该名全库唯一**时才算入链,否则同名折叠会给所有同名文件"发入链"、掩盖真孤篇 | 在 MOC 或项目说明里登记一行链接 |
| **A4** MOC 未覆盖 | 双口径:① 旧——`20-领域` + `50-资源` 下每篇是否出现在任一 MOC 文本里;② 新——`10-项目/<项目>/20-知识/` 的每篇是否出现在该项目 `00-索引.md` 里 | `40-归档`(只进不出)与 `90-模板` 不扫;有 `20-知识` 却缺 `00-索引.md` 时另报「项目索引缺失」 | 在对应 MOC 或项目索引里加一行 |
| **A5/A6** 元数据 | 缺 frontmatter / `type` 非 8 种规范值 / `status` 非 4 种 / 字段数 > 8 | 豁免:`00-索引`、`90-模板`、根 README、`10-项目/!问题追踪` | 按 README 的 schema 补齐或改值 |
| **A7** 路线一致性 | `00-索引/系统.md` 的「学习路线」与 `10-项目` **双向**一致,且项目 `status` 与产出相符 | 项目内除 `!项目说明.md` 外还有 `.md` → `learning`,否则 `todo`(`!实施计划.md` 计入"有产出") | 补路线条目,或改 `status` |
| **A8** 标签规范 | 同一标签的大小写冲突(`windows` 与 `Windows` 并存) | 只报"同一小写形式在别处也出现过"的大写写法,不误伤 `Linux`/`RFID` 这类专名 | 统一成库内约定的小写 |
| **A9** MOC 统计块 | 每张 MOC 顶部统计块的条目数、覆盖率末对 `n/m`、`最后校验` 日期与实物一致 | 覆盖率口径来自 `checks_extra.py` 的 `MOC_DIRS`(单一真源) | 用 `--coverage` 算出的真实数字改写统计块 |
| **A10** 知识归属 | `10-项目` 里的成品知识是否住进了项目/容器的 `20-知识/` | 只有路径形如 `10-项目/<某个目录>/20-知识/…` 才算合规(裸 `10-项目/20-知识/` 没有归属,照报);只查 `type` 为 `algorithm`/`language`/`system`/`concept`/`tutorial` 的(`project`/`note`/`log` 放哪都合规) | 搬进**所属项目或容器**的 `20-知识/`(`20-领域` 已不是正文归属地),或把 `type` 改成 `note`/`log` 表态 |
| **A11** 教学工作区 | 每个学习项目是否有 `teach` 状态层 | 有 `!项目说明.md` 的项目目录必须有 `MISSION.md` + `RESOURCES.md`,且**不能是空壳**(MISSION 要有 Why / Success / Constraints / Out of scope 四节,RESOURCES 要有 Knowledge / Gaps) | 按 `MISSION-FORMAT` / `RESOURCES-FORMAT` 补齐 |

## 四、内部怎么运作

### 4.1 文件分工(下表按主题列主要文件;每个自研文件都守 ≤200 行,超了就按主题拆)

| 文件 | 行数 | 职责 |
| --- | --- | --- |
| `vault_lib.py` | 188 | 公共库:定位仓库根、扫描 md、解析 frontmatter、抽链接/双链、白名单、A7 与统计辅助、教学工作区与容器识别 |
| `check_vault.py` | 200 | 入口:命令行参数、A1~A7 实现、汇总与退出码 |
| `checks_extra.py` | 197 | A8~A10 与 `--coverage`(按主题独立成文件,避免主入口超 200 行) |
| `checks_teach.py` | 51 | A11 教学工作区完整性(同样是为了不把主入口撑过 200 行) |
| `selftest_lib.py` | 51 | 公共库自检(7 项,含容器前缀边界) |
| `selftest_check.py` | 60 | A1~A6 自检(3 项:断链/孤篇/元数据、双链路径解析、裸双链同名不计数) |
| `selftest_extra.py` | 127 | A8~A10 自检(10 项:标签大小写、MOC 统计块、知识归属含「裸 `20-知识/` 没有项目归属」) |
| `selftest_a4.py` | 64 | A4 自检(3 项:旧口径扫 `50-资源`、项目索引缺登记/缺索引要报、按主干登记不得误报) |
| `selftest_teach.py` | 86 | A11 自检(5 项:缺文件要报、空壳要报、完整要过、非学习目录豁免、脚手架识别范围) |

每个文件都守着全局规则 **≤200 行**;当年 A8~A10 就是因此另开 `checks_extra.py`,而不是往入口里塞。

### 4.2 三个关键机制

**① 仓库根靠脚本位置反推**
`VAULT_ROOT = Path(__file__).resolve().parents[3]` —— 脚本在 `<仓库根>/50-资源/工具/vault-check/`,往上三层就是仓库根。所以整个工具**可以随库移动**,不需要改任何配置。

**② 先把代码"抹白"再扫链接**
`strip_code()` 把围栏代码块与行内代码**替换成等长空白**。这一步解决两个问题:代码里的 `[文字](网址)` 示例不会被当成真链接;同时**保持行号与列位置**,所以报错行号永远准确(如果直接删掉代码行,后面所有行号都会错位)。

**③ 白名单只写"故意为之"的东西**

- 链接白名单:模板占位路径、README 里的语法示例
- 双链白名单:刻意保留的「待补坑」,如 `[[快速排序]]`(留着提醒自己以后写)
- 豁免区:`00-索引`/`40-归档`/`90-模板` 允许孤立;`00-索引`/`90-模板`/根 README/`!问题追踪` 不要求 frontmatter
- 教学工作区协议文件(`MISSION.md`/`RESOURCES.md`/`NOTES.md`/`GLOSSARY.md` 与 `lessons/`/`reference/`/`assets/`/`learning-records/`)整体豁免 A3 与 A5-A6,也不计入 A7 的「项目产出」—— 它们是技能状态,不是库内笔记,由 A11 单独守

### 4.3 自检:检查器也要被检查

```bash
python -B selftest_lib.py     # PASS=7
python -B selftest_check.py   # PASS=3(A1~A6)
python -B selftest_extra.py   # PASS=10(A8~A10)
python -B selftest_a4.py      # PASS=3
python -B selftest_teach.py   # PASS=5
```

自检在**临时目录里造一个假库**,然后验证两类事:该报的报了(如放一个 `type: language` 的文件进 `10-项目`,A10 必须命中)、不该报的没报(如 `type: note` 的项目内每日笔记,必须不报)。**没有自检的检查器比没有检查器更危险** —— 它会给你一个虚假的"全绿"。

## 五、真实抓到的案例

| 时间 | 场景 | 谁抓到的 |
| --- | --- | --- |
| 2026-09-22 | 全库首次体检:断链 13 / 双链失效 29 / 孤篇 20 / 元数据 25 处 | A1~A6 |
| 2026-09-23 | 甲方案搬迁时,脚本把裸双链 `[[冒泡算法]]` 错改成 `[[路径.md]]`(Obsidian 不认)→ **33 处失效** | A2 |
| 2026-09-23 | 同轮:目录级链接(以 `/` 结尾)漏改 → 6 处断链 | A1 |
| 2026-09-23 | 两个"每日一练"项目的知识笔记迁走后,`status` 与内容不再相符 | A7 |
| 2026-09-23 | 重排 `20-领域` 后,新移入的 `Git.md`、`AI对话防断连.md` 没登记进 MOC | A4 |
| 2026-09-23 | 三张 MOC 的统计块数字过期(如"条目 45"而实物 46) | A9 |
| 2026-09-24 | 建教学工作区时发现 `checks_extra.py` 已 193 行,再加 A11 就破 200 行 → 另开 `checks_teach.py` | 行数纪律 |

**共同点**:这六类问题**都不会让任何东西报错**,笔记照样能打开、能提交、能推送 —— 只有专门去算才会发现。

## 六、边界:它查不到什么

| 查不到 | 原因 / 现状 |
| --- | --- |
| **内容对不对** | 只做结构检查;事实错误、逻辑错误、错别字(如 `palabas` 应为 `palabras`)它不知道 |
| **链接指向是否合理** | 只判断"目标存在",不判断"该不该链这里" |
| **图片是否可达** | `50-资源` 的图片不入库(只在本机),所以新克隆的机器上指向图片的链接会断 —— 这是**有意的取舍**,README 已写明 |
| **标签该不该打** | A8 只看形状与大小写冲突,不看语义 |
| **归档区** | `40-归档` 允许孤立、不查 MOC(只进不出) |
| **正文格式细节** | 那是 markdownlint 的活(仓库根有 `.markdownlint.jsonc`,目前 0 issues) |

## 七、给维护者:怎么加一条新检查

1. 在 `checks_extra.py` 写一个 `check_xxx() -> list[Finding]`(若是公共能力就放 `vault_lib.py`)
2. 在 `check_vault.py` 的 `groups` 列表里挂上,命名沿用 `A<n> 中文名`
3. 在对应的自检文件补**两个**用例:会命中、不会误报(A4 相关的放 `selftest_a4.py`,A7 与项目口径的放 `selftest_project*.py`,A8~A10 的放 `selftest_extra.py`,A1~A6 的放 `selftest_check.py`)
4. 同步更新 README 双语、本笔记的速查表
5. 守住 200 行上限(超了就按主题拆文件,像 A8~A10 那样)
6. 跑一遍全库确认新检查在真实库上为 0(否则说明规则与现状不一致,得先决定改规则还是改库)

**判据设计经验**:宁可"只报确定的问题"也不要"报一堆疑似"。例如 A8 只报**同一小写形式在别处也出现过**的大写标签,所以 `Linux`、`RFID` 这类只有一种写法的专名不会被误伤 —— 一个爱误报的检查器,很快就会被所有人忽略。
