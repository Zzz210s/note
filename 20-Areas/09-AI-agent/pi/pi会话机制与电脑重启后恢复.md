# pi 会话机制与电脑重启后的恢复

> 核心结论:**数据零丢失,进程不复活**。pi 会话自动落盘为文件,重启电脑后随时接回完整对话;但中断时正在执行的子进程/命令不会复活,需要重新触发。

## 一、会话存储机制

pi 的对话**自动保存**,不依赖任何手动操作:

- 保存位置:`~/.pi/agent/sessions/`(Windows 即 `C:\Users\<用户名>\.pi\agent\sessions\`)
- 存储形式:每个会话一个 JSONL 文件,消息逐条追加写入——重启/断电最多丢掉最后未写完的一轮
- **按工作目录分组**:目录名做转义,如 `--C--Users-23652--` 对应 `C:\Users\23652`,`--F--0-code--` 对应 `F:\0-code`
- 内部是**树结构**:每条记录带 `id` 和 `parentId`,同一文件内可分叉出多条对话路径(`/tree` 可回跳任意节点)

正因如此,重启电脑丢的只是终端窗口本身,对话状态一直躺在磁盘上。

## 二、重启后的恢复操作

### 启动参数(命令行)

| 命令 | 作用 |
|---|---|
| `pi -c` | 直接继续**最近一个**会话 |
| `pi -r` | 打开会话选择器,浏览搜索历史会话 |
| `pi --session <id>` | 恢复指定会话,id 支持**前缀部分匹配** |
| `pi --fork <id>` | 从历史会话**分叉**出新会话,不改动原文件 |
| `pi --name "任务名"` | 启动时就给会话命名 |

### 交互内命令(pi 已运行时)

| 命令 | 作用 |
|---|---|
| `/resume` | 同款会话选择器 |
| `/session` | 显示当前会话 ID、文件路径、消息数、token 消耗 |
| `/tree` | 在会话树内回跳任意历史节点继续(不建新文件) |
| `/name <名字>` | 给会话命名,重启后好找 |
| `/fork` | 从当前分支某条消息分叉出新会话文件 |
| `/clone` | 复制当前活动分支为新会话 |

### 选择器快捷键(`pi -r` / `/resume` 内)

- 搜索:直接输入关键词
- `Ctrl+P` 显示完整路径 | `Ctrl+S` 切换排序 | `Ctrl+N` 只看已命名会话
- `Ctrl+R` 重命名 | `Ctrl+D` 删除(有确认)

## 三、多并行会话的恢复实操

场景:同时开 3 个终端窗口跑 3 个 pi 任务(如代码修复、配置同步、调研),重启后全部丢失。还原步骤:

1. 重新开 3 个终端窗口
2. 每个窗口先 `cd` 到**原工作目录**(选择器只显示当前目录下的会话,目录不对就找不到)
3. 各自执行 `pi -r` 挑对应会话,或用 `pi --session <id前缀>` 精确恢复
4. 恢复后直接说"继续",模型读入全部历史接着干

**日常习惯**(让恢复更省事):

- 任务开始就 `/name ember修复` 命名,重启后 `pi -r` 里一眼可辨
- 关键任务可用 `/session` 记下会话 ID,之后 `pi --session 01a06183-4b67` 这样的前缀即可召回

## 四、边界:恢复的是对话,不是进程

- 恢复 = 把历史消息重新喂给模型,**重建上下文**;不是恢复操作系统进程
- 会话中断时**正在执行的东西不会复活**:进行中的 subagent worker、跑了一半的命令、内存里的状态全部消失,恢复后需要重新触发
- 若上次中断在"助手回答到一半",历史里会有半截消息,补一句指令让它继续即可
- 典型案例:任务因 API 429 限流中断,重启后 `pi -r` 恢复原会话,说"继续之前的任务"即可从中断点续做

## 五、与 tmux 的分工(互补关系)

| 工具 | 防什么 | 场景 |
|---|---|---|
| tmux | 防**连接断**(SSH 掉线、窗口关闭) | Linux/远程服务器,进程在 tmux 里继续跑 |
| pi session | 防**进程死/电脑重启** | 任何平台,对话历史落盘随时召回 |

Windows 本机跑 pi 时没有 tmux,靠的就是 pi 自身的会话机制;Linux 远程跑则两者叠加最稳。tmux 方案详见 [AI对话防断连](<../../04-系统与部署/Linux/AI对话防断连/README.md>)。
