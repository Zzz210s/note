# 测试夹具(Test Fixture)是什么

> 读项目报告时常看到这类句子:「**16 个夹具 runner 全部 FAIL=0(约 628 条断言)**」「docs 夹具 65/0」「l4 夹具 98/3 -> 101/0」。
> 这里的"**夹具**"到底指什么?本文讲清楚这个词的三层含义、它为什么叫夹具、以及在本机双系统部署项目里的具体形态。
> **本文的固定写法**:每个概念按「**为解决什么痛点而生 / 一句话定义 / 大白话注解**」三段给出。
> 关联阅读:[编辑器,编译器,IDE的区别](<编辑器,编译器,IDE的区别.md>)。

---

## 一句话速览

| 名称 | 一句话定义 | 大白话注解 |
| --- | --- | --- |
| **夹具(fixture)** | 为测试预先固定好的**输入条件**(数据、环境、样例文件),使每次运行都在同一前提下进行 | "把工件夹住再加工"—— 前提固定了,结果才可比较 |
| **夹具运行器(runner)** | 逐个把夹具喂给被测程序、并逐条核对结果是否等于预期的脚本 | 一条命令跑完一整套检查 |
| **断言(assertion)** | 一条"结果必须等于 X"的判定,命中记 PASS、不命中记 FAIL | 每问一句"对不对?",答案只有对/错 |
| **`PASS=n FAIL=m`** | 运行器跑完输出的收口统计 | 前面 n 条断言通过、m 条不通过 |

---

## 一、三层含义:先说清"夹具"到底指哪个

"夹具"是英文 **fixture** 的翻译,在不同场合指不同东西 —— 这也是最容易糊涂的地方。

### 1. 固定测试条件的"夹具"(业界经典含义)

> **为解决什么痛点而生**:同一个功能,这次测能过、下次测又不行 —— 因为测试**开始时机器上的状态不一样**(数据库里有旧数据、临时目录残留上次的文件、时区/环境变量不同)。原因没变、结果却变了,测试就失去可信度。
> **一句话定义**:夹具是**在测试执行前把系统置入某个确定状态、并在结束后恢复原状**的机制(通常成对出现:准备 setUp / 收尾 tearDown)。
> **大白话注解**:就像上台表演前先把布景、灯光、道具摆成固定位置 —— 每次开演前都一样,观众(测试)看到的差异就只能来自演员(被测代码)。

常见形态:测试数据库的初始数据、临时目录、环境变量、启动好的服务进程。Python 的 `@pytest.fixture`、单元测试框架里的 `setUp/tearDown` 都是干这个的。

### 2. 作为输入的"样例文件"(常驻样例)

> **为解决什么痛点而生**:要验证"检查工具能识别出坏写法",就得先有**坏写法的样本**;每次手工造样本既费时又不一致。
> **一句话定义**:夹具是**一组预先准备好的输入样例**(小仓库、样例文档、坏配置),被测试程序读入以触发特定分支。
> **大白话注解**:考试前老师准备的"标准题卡" —— 每道题都想好了要考哪个知识点。

### 3. 本项目里最常见的用法:夹具 = 一个可独立运行的测试脚本

> **为解决什么痛点而生**:交付物是一堆 shell/PowerShell 脚本与手册,靠人工点一遍验证**不可重复、漏得多、也说不清"到底验过什么"**。
> **一句话定义**:夹具是**一个自包含的测试脚本**(runner),它准备好输入、调用被测脚本,并列出一组断言、最后打印 `PASS=n FAIL=m`。
> **大白话注解**:把"验收清单"写成代码 —— 机器照着清单逐条问"对不对",最后报"过了几条、错了几条"。
> 一句话区分:**含义 1、2 是"前提/原料",含义 3 是"把前提和检查打包在一起的那套装置"**。项目报告里说的"16 个夹具 runner",用的是含义 3;而 `scripts/repo/tests/check-docs/` 下的 `c1/`、`c7/`、`tmp-repo/` 这些目录,用的是含义 2。

## 二、为什么叫"夹具"

这个词借自**机械加工**:

- 车床/铣床上,工件不能用手按着加工 —— 得用**夹具(clamp/jig)**把工件**固定在确定位置**;
- 位置固定了,刀具每次走的路径才有意义,加工结果才能**重复**;
- 换一个工件、装进同一个夹具,就能**用同一套程序加工**。

软件测试借的是同一个隐喻:**把"被测对象的前置条件"固定住,让"每次运行"具有可比性**,再让同一套检查程序反复使用。

## 三、本项目实例:16 个运行器 / 约 628 条断言

以本机《Windows 与 Ubuntu 双系统部署》playbook 项目(`F:\0-code\20-active\tool-win-linux-dualboot`)为例。

### 放在哪里

| 位置 | 内容 | 是否入库 |
| --- | --- | --- |
| `.superpowers/sdd/silverblue/fixtures/<主题>/` | 15 个运行器(`run-fixtures.sh` / `run-fixtures-ps.sh` / `run-fixtures-ps-l2.sh`) | **不入库**(AI 产物) |
| `scripts/repo/tests/check-docs/` | 1 个运行器 + 常驻样例 `c1/ … c9a/ ok/ tmp-repo/` | 入库(版本化测试套件) |

合计正是报告里的 **16 个夹具 runner**。

### 一个运行器长什么样

以总控脚本 `scripts/linux/dbk.sh` 的夹具为例(节选):

```bash
#!/usr/bin/env bash
# 总控入口 scripts/linux/dbk.sh 的夹具(非交付物,位于 .superpowers/,不入库)。
# 覆盖:分发与汇总、破坏性门槛、未知步骤 -> 64、参数透传、--json 汇总、--log 落盘。
set -uo pipefail
REPO="${REPO_ROOT:-$(cd "$HERE/../../../../.." && pwd)}"
. "$HERE/fixture-lib.sh"
```

公共库 `fixture-lib.sh` 提供三样关键工具:

| 工具 | 作用 |
| --- | --- |
| `ok "说明"` / `bad "说明"` | 累加计数器并打印 `PASS 说明` / `FAIL 说明` |
| `expect 说明 期望rc [stdout含] [stderr含]` | 一条完整的断言:退出码、标准输出、标准错误都要对上 |
| `finish` | 打印 `PASS=n FAIL=m`;只要 `FAIL` 非 0 就以退出码 1 结束 |

于是"断言"落地成很朴素的东西 —— **对退出码和输出文本的逐条比对**:

```bash
run --dry-run
expect "破坏性门槛:未加 --yes 应退 2" 2 "" "--yes"
```

### runner 的嵌套汇总

`l4` 的运行器会**把上一批 `cli-05` 夹具的 42 条结果计入自己总数**:

```bash
cl="$(printf '%s\n' "$cli_out" | grep -E '^PASS=[0-9]+ FAIL=[0-9]+$' | tail -n1)"
# 解析 PASS=/FAIL= 后累加到本运行器的计数器
```

这也是报告里出现 `l4 101` 这种"大于本文件内联断言数"的原因。

### 报告里的数字怎么拆

| 运行器 | 断言数 | 说明 |
| --- | --- | --- |
| cli-05 | 42 | 命令行契约 |
| dbk | 32 + 24 | 总控脚本 bash 版 + PowerShell 版 |
| dbk-cli | 39 + 25 | 契约库 bash 版 + PowerShell 版 |
| l0 | 31 | 基础层 |
| l3 | 20 + 6 | 基础层 bash + PS |
| l4 | 101 | 首启层(含 cli-05 的 42 条汇总) |
| partitions | 23 | 分盘前置章节 |
| rescue | 108 | 救援层 |
| verify | 17 | 验证层 |
| windows-track | 46 + 29 + 17 | Windows 轨道 bash + PS + PS-L2 |
| repo | 68 | `scripts/repo/tests/` 下 check-docs 系列 |
| **合计** | **约 628** | **16 个运行器,`FAIL=0`** |

### 两条容易被忽略的规矩

1. **夹具不入库**。`.superpowers/` 下的运行器是**测试装置**,不是交付物 —— 交付的是脚本与手册,夹具只保证它们没坏。
2. **"夹具级验证"不等于"真机验证"**。项目契约要求:凡**没在真机上跑过**的东西,必须在脚本头与文档中**显式声明**,不许用夹具通过来暗示真机可用 —— 夹具证明的是"逻辑与契约",不是"硬件上真的能启动"。

## 四、怎么读这些数字

| 报告写法 | 含义 |
| --- | --- |
| `docs 夹具 65/0` | `PASS=65 FAIL=0`,全通过 |
| `l4 夹具 98/3 -> 101/0` | 从"98 通过 3 失败"修到"101 通过 0 失败" |
| `全部 FAIL=0` | 唯一判据:**失败数必须为 0**,通过数多少只表示覆盖量 |
| `夹具 F7 断言` | 运行器里编号/命名的某一条断言(对应某个契约条款) |

一个值得记住的实践:**当夹具报红时,先判断是"夹具写错了"还是"被测代码错了"。** 该项目 B2 轮 3 个 l4 夹具失败的根因是**脚本缺陷**(`collect-l4.sh` 里赋值语句被上一行注释吞掉,`set -u` 抛 unbound variable)—— 于是**改脚本、不改夹具**。夹具本身也是被审查对象:它一旦放宽,等于把风险藏起来。

## 五、和相邻术语的关系

| 术语 | 一句话定义 | 与夹具的关系 |
| --- | --- | --- |
| **单元测试** | 针对最小代码单元(一个函数)的测试 | 常需夹具提供初始数据 |
| **集成测试** | 验证多个组件协同是否正确 | 夹具更重(要起服务、建临时仓库) |
| **端到端(E2E)** | 从用户入口到尾端结果的完整链路测试 | 夹具 = 整套环境 |
| **冒烟测试** | 只验证"主要功能还能跑起来"的最小集合 | 可视为夹具的一个子集 |
| **stub / mock** | 用假的替身替代真实依赖,以便隔离被测对象 | mock 常作为夹具的一部分被注入 |
| **断言** | 一条"结果必须等于 X"的判定 | 夹具运行器的组成单元 |

**一句话总结**:夹具负责"把前提固定住",断言负责"逐条问对不对",运行器负责"跑完收口报数" —— 三者合起来,才是报告里那句"16 个夹具 runner 全部 FAIL=0"。
