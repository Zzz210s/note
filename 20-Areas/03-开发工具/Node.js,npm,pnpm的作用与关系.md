# Node.js、npm、pnpm 的作用与关系

> 一句话先记住:**Node.js 是"发动机",npm / pnpm 是"应用商店 + 快递员",package.json 是"购物清单",node_modules 是"收货仓库"。**
> 本文用大白话讲清每个东西是干嘛的、谁包含谁、为什么会有这么多"pm",最后附命令对照表和本机实测版本。

## 一、一分钟版本(先看这张图)

```text
Node.js(运行时 = 发动机)
 ├─ 自带 npm       ← 包管理器(应用商店)
 ├─ 自带 npx       ← 临时试用工具(不长期装)
 └─ 自带 corepack  ← 管"包管理器自己的版本"的管家
        │
        │ corepack 可以帮你拉起 yarn / pnpm
        ↓
npm  /  pnpm  /  yarn   ← 三个"应用商店",三选一
        │  从网上的仓库(registry)下载别人写好的代码包
        ↓
node_modules/           ← 下载来的包,堆在项目里的这个文件夹
        ↓
你的代码 import / require 这些包,就能用了
```

**关系一句话**:装 Node.js 就有了 npm;npm 用来装别人的包;pnpm 是"更好用的 npm";它们都在同一层干活,**一个项目只该用一个,别混**。

## 二、Node.js:让 JavaScript 走出浏览器的"发动机"

### 它是什么

JavaScript 这门语言,一开始**只能活在浏览器里** —— 浏览器负责"解释并运行"它。

**Node.js 就是给 JavaScript 装的一台通用发动机**:它把浏览器里那个"跑 JS 的引擎"(V8)单独拎出来,配上"读写文件、开网络端口、跟操作系统打交道"的能力,于是 JS 就能**离开浏览器,直接在电脑上跑**。

### 大白话类比

- 以前:JS 是"只能在泳池里游泳的鱼"(泳池 = 浏览器)。
- 有了 Node:这条鱼长了腿,能上岸到处走了 —— **能写后端服务、能写命令行工具、能写自动化脚本、能跑前端构建**。

### 它能干什么(为什么到处都是它)

| 用途 | 例子 |
| --- | --- |
| 跑前端构建工具 | Vite、Webpack 本身是 JS 写的,靠 Node 运行 |
| 写后端服务 | Express、Nest、Fastify |
| 写命令行工具 | 各种 `xxx-cli`(包括本机很多工具) |
| 写自动化脚本 | 批处理文件、爬取、数据清洗 |
| 自带实用能力 | 内置 `fs`(文件)、`path`(路径)、`http`(网络)等模块;本机 Node 24 还内置了 `node:sqlite`(直接开箱用 SQLite) |

### 容易混的点

- **Node.js 不是语言**,语言是 JavaScript;Node 是"运行环境"(runtime)。
- **Node 不是浏览器**:浏览器有 `window`、`document`;Node 有 `process`、`fs`。同一个语言,两套环境。
- **Node 版本很重要**:不同项目可能要不同 Node 版本 → 于是有 `nvm-windows` / `fnm` / `volta` 这类"版本切换器"。

## 三、npm:Node 自带的"应用商店 + 快递员"

### npm 是什么

**npm = Node Package Manager(Node 包管理器)**。写代码不该啥都自己造 —— 别人已经把常用功能打包好了(就叫"**包**"或"**依赖**")。npm 负责:

1. 去**仓库(registry,默认 registry.npmjs.org)** 找到你要的包;
2. **下载**到你的项目里;
3. **记录清单**,下次别人拉你的代码能一键装出一模一样的环境;
4. 顺便**管版本**:升级、降级、看依赖关系。

**关键点:装 Node.js 的时候就顺手装了 npm。** 本机在 `C:\Program Files\nodejs\` 里能直接看到 `npm`、`npx`、`corepack` 和 `node.exe` 摆在一起 —— 它们是"一起来的"。

### 必须认识的 4 样东西

| 名字 | 大白话 | 文件形态 |
| --- | --- | --- |
| **package.json** | 项目的**身份证 + 购物清单**:我叫啥、什么版本、要买哪些包、有哪些快捷脚本 | `package.json` |
| **lockfile**(锁文件) | 精确到"最小版本"的**购物小票**:保证你和同事、和服务器装出来的完全一样 | npm 用 `package-lock.json`,pnpm 用 `pnpm-lock.yaml` |
| **node_modules/** | 快递收货的**仓库**:下载来的包真身都堆在这 | 文件夹(通常巨大,不进 Git) |
| **registry** | **商店地址**:默认是 npm 官方源;国内常换成镜像加速 | 配置项,不是文件 |

### 顺带懂一下"版本号"

形如 `1.2.3` = **主版本.次版本.修订号**。写在 package.json 里时前面常有符号:

| 写法 | 意思 | 说明 |
| --- | --- | --- |
| `^1.2.3` | 允许升到 `1.x.x` 里最新(不跨主版本) | 最常见 |
| `~1.2.3` | 只允许升到 `1.2.x` 里最新 | 更保守 |
| `1.2.3` | 就锁死这个版本 | 最保守 |

> 口诀:**主版本变了 = 可能不兼容**(1.x → 2.x 可能要改代码);所以 `^` 是"小步更新可以,别跳大版本"。

## 四、pnpm:为什么还要再造一个"应用商店"

先看 npm 的几个老毛病:

| 痛点 | 具体表现 |
| --- | --- |
| **占磁盘** | 每个项目的 `node_modules` 都是真实文件的一份拷贝。同一个包在 20 个项目里,就存 20 份 |
| **装得慢** | 因为要真的复制几十万个小文件 |
| **幽灵依赖** | npm 为了让 `require` 找得到包,把依赖"拍平"摊在最外层。结果你能 `import` 一个**你根本没在 package.json 里声明**的包 —— 今天能跑,明天上游一改就崩 |
| **不确定性** | 安装顺序、目录结构在不同机器上可能不一致 |

**pnpm(= performant npm,"性能版 npm")就是冲着这几条来的**:

### 它的三招

1. **内容寻址存储(content-addressable store)**
   全机只留**一份**包仓库(类似 git 的对象库):包按内容哈希存放,**内容一样的包永远只存一份**。
   - 本机实测:`pnpm store path` → `F:\.pnpm-store\v11`
2. **硬链接(hard link)代替复制**
   项目里不再放包的"拷贝",而是放一个指向仓库的"链接"。文件只有一份,但每个项目都"看得到"。
   - 于是:装得快、占得少。100 个项目共享同一份包。
   - 小坑:**硬链接要求"仓库"和"项目"在同一个磁盘分区**。如果 store 在 `F:` 而项目在 `C:`,就只能退化成复制,省磁盘的好处就没了。
3. **严格的 node_modules 结构(符号链接树)**
   每个包只能访问**自己声明过**的依赖,访问不到"别人家的"。幽灵依赖直接报错 —— 问题提前暴露,而不是上线那天才炸。

### 直观感受差别

| 场景 | npm | pnpm |
| --- | --- | --- |
| 第 1 个项目装 lodash | 下载 + 复制 | 下载入库 + 链接 |
| 第 2 个项目再装 lodash | **又复制一份** | **直接链接,几乎不占新空间** |
| 装 20 个项目的常用依赖 | 磁盘吃紧 | 磁盘几乎不变 |

> 结论:**pnpm 不是"另一个功能",而是"同一件事做得更省更快更严格"。** 学它的成本几乎为零 —— 命令换来换去就那么几条(见下表)。

## 五、全家福:谁是谁,别搞混

| 名字 | 是什么 | 一句话 | 要不要用 |
| --- | --- | --- | --- |
| **Node.js** | 运行时 | 让 JS 在电脑上跑 | 必须有 |
| **npm** | 包管理器 | 随 Node 自带,最通用 | 默认就用它 |
| **pnpm** | 包管理器 | 更省磁盘、更快、更严格 | 新项目推荐 |
| **yarn** | 包管理器 | npm 的老对手(Facebook 出品),当年为"快"而生 | 老项目里常见,跟着 lockfile 走 |
| **npx** | 一次性执行器 | 临时跑一个包里的命令,**装完就走,不留垃圾** | 随 npm 自带 |
| **corepack** | 包管理器版本管家 | 让"项目指定的 pnpm/yarn 版本"自动生效 | 随 Node 自带(本机 0.34.6) |
| **nvm-windows / fnm / volta** | Node 版本切换器 | 这台机器上同时装多个 Node 版本,按项目切换 | 当你需要多版本时 |

**npx 举个栗子**:你只想试一次某个工具,不想全局安装污染环境 →

```bash
npx 某工具 --help      # 临时下载并运行,用完即走
```

**corepack 干嘛的**:pnpm / yarn 更新很频繁,而"某个项目必须用 pnpm 9"这种事很常见。corepack 就是"项目里声明用哪个版本,它就自动切到那个版本",避免"我这儿能跑你那儿报错"。

## 六、命令对照表(npm ↔ pnpm)

| 想干什么 | npm | pnpm |
| --- | --- | --- |
| 初始化项目 | `npm init` | `pnpm init` |
| 装清单里的全部依赖 | `npm install` | `pnpm install` |
| 加一个依赖 | `npm install 包名` | `pnpm add 包名` |
| 加开发依赖(不打包进产品) | `npm install -D 包名` | `pnpm add -D 包名` |
| 删依赖 | `npm uninstall 包名` | `pnpm remove 包名` |
| 跑 package.json 里的脚本 | `npm run dev` | `pnpm dev`(也能 `pnpm run dev`) |
| 全局装一个工具 | `npm install -g 包名` | `pnpm add -g 包名` |
| 看装了哪些包 | `npm ls` | `pnpm list` |
| 更新包 | `npm update` | `pnpm update` |
| 清缓存 | `npm cache clean --force` | `pnpm store prune` |

规律很好记:**npm 里凡是要"管包"的动作,多半换成 `add` / `remove` / `list`;pnpm 的 `run` 还能省掉。**

## 八、实用建议与踩坑

1. **一个项目只用一个包管理器**。npm 和 pnpm 的 lockfile 不同,混着用会互相打架、锁文件来回改。跟着项目里已有的 lockfile 走:
   - 看到 `package-lock.json` → 用 npm
   - 看到 `pnpm-lock.yaml` → 用 pnpm
   - 看到 `yarn.lock` → 用 yarn
2. **`node_modules` 不要进 Git**,但要**把 lockfile 提交进 Git** —— 一个装不下,一个是"必须带上"。
3. **不要手改 node_modules**,它随时会被重装覆盖;要改就用"打补丁"工具(patch-package 之类)。
4. **磁盘紧张时**:`pnpm store prune` 清掉仓库里没人用的包;npm 用户注意"每个项目一份"的特性。
5. **国内下载慢**:换镜像源能明显加速,但要注意"锁文件里的地址"也可能被写进镜像地址,团队协作时保持一致。
6. **装不上/报错先看版本**:很多"玄学 bug"其实是 Node 版本不对或缓存脏了 ——
   - 清缓存重装:`pnpm store prune` / 删 `node_modules` + `pnpm install`
   - 查版本:`node -v`、`pnpm -v`
7. **别迷信"全局安装"**:能装在项目里就装在项目里(不同项目可能要不同版本);只装"一次性工具"时用 `npx`。
