# 夹具与门禁质量审查报告：tool-win-linux-dualboot（HEAD bedc90b / v0.2.5）

审查对象：`.superpowers/sdd/2026-09-25-atomic-restore-and-distro-interface/fixtures/`（k1 = Linux 侧、windows = Windows 侧）与 `scripts/repo/check-docs*.sh`、`scripts/repo/check-scripts.sh`。
约束遵守：仓库内零改动（`git status --porcelain` 全程为空）；所有变异都在 `/tmp` 副本里做。
副本路径：`/tmp/fx/tool-win-linux-dualboot`（= 纯净基线，下文称 BASE）、`/tmp/fx/mut`（= 变异工作副本）、`/tmp/fx/gate`（= 门禁副本）；均由 `tar cf - --exclude=.git tool-win-linux-dualboot | (cd <目标> && tar xf -)` 生成。
单文件跑夹具的临时运行器（不在仓库内）：`/tmp/fx/run-k1.sh`、`/tmp/fx/run-win.sh`（source 对应 lib.sh + 指定 case 文件 + `sum`）。

## 结论（先给）

夹具不是空转的：9 个变异里 6 个立刻变红（sha256 校验、pinned 标记、需人工=2 的退出码、44 条计数、-Check 落盘、-Json 单行），说明大部分"关键声明"真有守卫。

但有 3 处**实现改坏了夹具仍然全绿**：
1. `windows/case-restore-esp.sh:109` 有个 bash 引号转义 bug，整文件在 114 行解析失败，**R10/R11/R12 三条用例从未执行**；runner 依旧打印 `PASS=187 FAIL=0`。
2. `windows/case-l0l2.sh:87` 的 `! calls_has displayorder` 是**结构恒真**（那个用例没接假 bcdedit，calls.log 永远不可能出现该串）——而且真机撞上这条路径会去调 **真实** `C:\Windows\System32\bcdedit.exe`。
3. `scripts/windows/dbk-win-probe.ps1:172` 的"BootOrder 首位必须是 Windows"前置断言、`scripts/windows/verify-baseline.ps1:99` 的 ① 比对，都没有任何夹具能让它们失败。

另外 4 条断言恒真（`mount` / `fallocate` / `mkswap` / `apt-get` 在 `fixtures/k1/bin` 里没有假件），以及一个系统性盲区：**零写快照只覆盖 `$case/data/`**，而沙箱还给了脚本 `home/`、`mnt/`、`base/`、`bak/` 等可写目标。

门禁两侧各有多条"违规但绿灯"：check-docs 漏子目录文档、漏部分 emoji、漏 6 类扩展名以外的坏链、C9b/C9c 非递归；check-scripts 的 200 行上限用 `wc -l`（无尾换行少算 1 行）、S-1 只认 apt/dpkg/dnf/snap/rpm-ostree。

## 一、恒真断言（永远为真 / 几乎不可能为假）

### T1 `windows/case-l0l2.sh:87` —— 结构恒真，且真机有副作用风险（最严重）

```bash
verdict "$([ "$rc" -eq 0 ] && zw "$d" && ! calls_has "$d" 'displayorder' && ...)"
# 用例名：R2 restore-boot-order -Check 首位是 Windows -> 0 且零写、不改 displayorder(I2)
```

证据（结构性）：`calls.log` 只由 `$WORK/psbin` 下的假件写（`windows/lib.sh:9-11`），而该用例（`case-l0l2.sh:67-74`）只设了 `DBK_IS_ADMIN/DBK_BM_TEXT/DBK_FW_TEXT`，**没有设 `DBK_BCEDIT_EXE`**；`psbin` 里的 bcdedit 假件只有 `bcdedit-rep.cmd` / `bcdedit-decom.cmd` 两个名字，没有 `bcdedit.cmd`，也不在 PATH 上。因此 `calls.log` 里不可能出现 `displayorder` 这个词 —— 任何实现都让这条断言恒真。

证据（实证，安全做法）：在 `/tmp/fx/mut/scripts/windows/restore-boot-order.ps1:71` 插入一次真实调用
`$null = Invoke-DbkProbeExe -Exe 'bcdedit' -CmdArgs @('/set','{fwbootmgr}','displayorder','{bootmgr}')`，
并**先用 PATH 前置一个记录用的 `bcdedit.cmd` 桩**（`/tmp/fx/danger/bcdedit.cmd`，避免真的改本机固件启动顺序）：

```bash
cd /tmp/fx && PATH="/tmp/fx/danger:$PATH" bash run-win.sh /tmp/fx/mut case-l0l2.sh
# 结果：PASS=12 FAIL=0（含 M8 正向对照与 R2 两条都绿）
# 桩件日志 /tmp/fx/danger/called.log 出现两行 bcdedit /set {fwbootmgr} displayorder {bootmgr}
```
即：**变异确实执行了改序命令两次，夹具全绿**。

后果：这条本应钉住不变量 I2（"永远不用 displayorder 改序"）的用例，只在"实现恰好不调用 bcdedit"时成立；一旦回归，本机（`command -v bcdedit` → `/c/WINDOWS/system32/bcdedit`，`C:\Windows\System32\bcdedit.exe` 509 KB 在 PATH 上）会被真实改序，且夹具不会报错。夹具头注释里写的"实测该路径零外部调用"是事实，但下一句"补一条正向断言证明不是空转"只证明了**走到了读基线 BootOrder 的判据**（输出文本），证明不了"没调外部命令"。

最小修法：该用例补 `export DBK_BCEDIT_EXE="$(wp "$PSBIN/bcdedit.cmd")"`，并生成一个通用 `bcdedit.cmd` 假件（把调用记进 `%DBK_CALLS%` 后 `exit /b 1`）；这样断言可真假两态，且真机不会被误调。

被断言脚本：`scripts/linux/storage.sh`（S3 `--check` 零写）。

## 二、零写 / 零外部动作覆盖盲区

### Z1 结构性盲区：`zw` 只快照 `$case/data/`，沙箱其余可写目标不进快照

`k1/lib.sh:20` `D() { printf '%s/data' "$1"; }`、`k1/lib.sh:36 snap()`、`k1/lib.sh:45 zw()`；Windows 侧同理 `windows/lib.sh:21/26/35`。
但用例沙箱里，mkinst 给脚本准备了 `$CD/bin $CD/mnt $CD/home $CD/base`（`k1/case-l4-cards.sh:11-12`，且在 `--apply` 里脚本本来就该写 `$CD/home/.config/user-dirs.dirs`）；Windows 侧 `case-verify-all.sh:26-30` 还准备了 `$d/git`。

举证（实证）：把 `scripts/linux/xdg-redirect.sh` 改成**任何模式下**都在 `$DBK_HOME` 里落一个文件
（插在 `/tmp/fx/mut/scripts/linux/xdg-redirect.sh:38`：`[[ -n "$HOMEDIR" ]] && { mkdir -p "$HOMEDIR"; : > "$HOMEDIR/dbk-check-junk"; }`）：
```bash
bash run-k1.sh /tmp/fx/mut case-l4-cards.sh      # PASS=15 FAIL=0
find .../k1/.tmp -name 'dbk-check-junk'          # .tmp/xdg-apply/home/dbk-check-junk 确实被创建
```
`--check` 分支写盘（X2 "xdg-redirect --check 已写入后 -> 0 且零写"）完全没被发现。

后果：所有 `--check`/`-Check` 的"零写"承诺，实际只覆盖 `data/`；脚本若把东西写到 `home/`、`mnt/`、`base/`、`bak/`（都是夹具交给它的真实目标目录）就漏检。
最小修法：`snap_begin`/`zw` 改成快照整个用例目录，排除 `calls.log`、`snap-*.txt`、`log.txt`、`stdout.txt`、`stderr.txt`、`seen-*` 这些夹具自身的记录件。

### Z2 25 条（k1）+ 22 条（windows）verdict 只断 `zw`、不断 `calls.log`

`windows/lib.sh:49 noyes()` 与 `windows/lib.sh:55 gate64()` 都带 `[ ! -s "$d/calls.log" ]`，所以走这两个 helper 的用例是齐的；**手写 verdict 的那些就漏了**。具体清单（`文件:行`）：

|---|---|---|
| `k1/case-l4-cards.sh:59` | mount-shared `--apply` 缺 `--yes` → 64 | `calls.log` 为空 |
| `k1/case-l4-cards.sh:82` | xdg-redirect `--apply` 缺 `--yes` → 64 | 同上 |
| `k1/case-l4-cards.sh:106` | upgrade-release `--apply` 缺 `--yes` → 64 | 同上 |
| `k1/case-l4-cards.sh:147` | reboot-to-windows 无 efibootmgr → 9 跳过 | 同上 |
| `k1/case-l4-gate.sh:24,28,36,40,44` | 五个 `--apply` 缺 `--yes` 门槛 | 同上 |

## 三、未覆盖分支（零断言的函数 / 分支）

### U1 `windows/case-restore-esp.sh:109` 语法错误 → 三条用例静默消失（最严重）

```bash
:109:  ... "R13 备份含 EFI/fedora/ 条目也不还原 -> 0 且 ESP 上无 \EFI\fedora\" "rc=$rc out=$out"
```
`\E`、`\f` 是字面反斜杠，但句尾 `\"` 在双引号里是**转义引号**（不是"反斜杠 + 结束引号"），字符串因此没结束，整文件解析失败。

实证：
```bash
cd <仓库>/.../fixtures/windows && bash -n case-restore-esp.sh
# case-restore-esp.sh: line 114: syntax error near unexpected token `('   rc=2   ← 仓库原文件即如此
bash run-win.sh <BASE> case-restore-esp.sh      # PASS=14 后中止（应为 17）
grep -n 'case-restore-esp' run-fixtures.sh      # 30:. "$HERE/case-restore-esp.sh"
```
`windows/run-fixtures.sh:30` 用 `.` source 它，bash 解析到 114 行报错并**放弃该文件剩余部分**，但 runner 没有 `set -e`，后续 case 文件照跑，最后打印 `PASS=187 FAIL=0`。

消失的三条：`R10 DBK_IS_ADMIN=0 -> 2 且零写`（`:114`）、`R12 -Step 99-9 -> 64`（`:116`）、`R11 -Json 只输出一行 JSON`（`:118`）。
最小修法：`...\EFI\fedora\"` → `...\EFI\fedora\\"`（或删掉末尾反斜杠）；并给 `run-fixtures.sh` 加一条自检（每个 case 文件 source 前 `bash -n`，或断言预期 PASS 数）。顺带：`.superpowers/**` 下的夹具不在任何门禁的扫描范围内（`check-scripts.sh:39` 只 `find "$ROOT/scripts"`），所以这类语法错误没有任何自动拦截。

### U2 `scripts/windows/dbk-win-probe.ps1:172` —— `Assert-DbkFwPre` 的"首位必须是 Windows"失败分支零覆盖

变异：`172s/if (-not ($first -eq '{bootmgr}' -or $fd -match $script:DbkProbeWbm))/if ($false)/`
```bash
bash run-win.sh /tmp/fx/mut case-repair-boot.sh                     # PASS=19 FAIL=0
bash run-win.sh /tmp/fx/mut case-bootnext.sh case-decommission.sh   # PASS=58 FAIL=0
```
全绿。调用方 `cleanup-nvram`、`delete-linux-partition`、`disable-linux-entry`、`extend-data-partition`、`restore-boot-order(-Apply)` 都没有"固件首位不是 Windows → 64"的用例（`restore-boot-order` 传 `-SkipOrderCheck`，`repair-windows-boot` 走自己的逻辑）。
后果：这几条破坏性脚本的"先验顺序守卫"失守不会被发现。
最小修法：给 `cleanup-nvram`/`disable-linux-entry`/`extend-data-partition` 各加一条：`DBK_FW_TEXT` 用 fedora 在首位的文本 → 期望 64 且零写零外呼。

### U3 `scripts/windows/verify-baseline.ps1:98-99` —— ① 比对逻辑在夹具里不可达

变异：`99s/.*/  $ok = $true/` → `bash run-win.sh /tmp/fx/mut case-cli-contract.sh` = `PASS=15 FAIL=0`。
原因：`verify-baseline.ps1` 的夹具钩子只有 `DBK_IS_ADMIN`/`DBK_MOUNTVOL_EXE`（脚本头自述），**没有 `DBK_FW_TEXT`**，固件文本只能来自真实 `bcdedit /enum firmware`；非管理员会话下 `Get-FirmwareText` 返回 `$null`，① 永远走 `if (-not $fw)` 那条失败分支。夹具对 ① 只断言"输出了这一行"（`windows/case-cli-contract.sh:45,64,67` 的 `has "$out" '① BootOrder 首位 -> '`），从不断言判定结果。
最小修法：给 `verify-baseline.ps1` 加 `DBK_FW_TEXT`/`DBK_BM_TEXT` 钩子（与 `dbk-win-probe.ps1` 同口径），再补两条用例：Windows 首位 → ① 通过、fedora 首位 → ① 失败。

### U4 Linux 侧 `--json` 契约零覆盖

`scripts/linux/dbk-cli.sh:9` 声称"`--json` 时 stdout 只有 exit 的一行 JSON"（实现在 `dbk-obs.sh`）。`grep -n -- '--json' k1/case-*.sh` 只命中两处**注释**（`case-l4misc.sh:152`、`case-rollback-deploy.sh:14`，说的是**假 rpm-ostree** 的 `--json`），**没有任何 k1 用例把 `--json` 传给它测的步骤脚本**。Windows 侧同契约有 C3/-Json（`windows/case-cli-contract.sh:76-80` 等）钉着。
最小修法：在 k1 里挑 2-3 个脚本（如 check-health.sh、verify-all.sh、某个破坏性脚本）加 `--json` 用例：stdout 恰一行、`{"step":...}` 前缀、stderr 允许有内容。

### U5 `-Step` 覆盖只有 7 个 case 文件

含 `-Step` 的：`case-bootnext.sh`(set-bootnext)、`case-cli-contract.sh`(preflight / verify-baseline / dbk.ps1)、`case-media.sh`(verify-install-media)、`case-partlayout.sh`(check-partition-layout / create-partitions)、`case-repair-boot.sh`(repair-windows-boot)、`case-restore-esp.sh`(restore-esp，**U1 已死**)、`case-verify-all.sh`(verify-all)。
零 `-Step` 用例的步骤脚本：backup-esp、check-activation、check-firmware、check-gate、cleanup-nvram、collect-l0、collect-l1、collect-l2、delete-linux-partition、disable-faststartup、disable-linux-entry、extend-data-partition、redirect-known-folders、restore-boot-order、verify-windows-baseline。
（`-Step` 校验在共享库里，纯逻辑风险低；但**每脚本的卡头集合**是各写各的，`Assert-DbkStep` 对"某脚本的卡头写错"只有靠这几条用例才能发现。）

### U6 `scripts/linux/storage.sh:83-86` —— ④休眠 三个分支只覆盖一个

覆盖的是"cmdline 可读且无 `resume=`"。零用例：`resume=` 命中（→ 需人工）、`$CMDLINE` 读不到（→ 需人工）。同类"需要 2/9 的多态分支"在 check-health.sh（显卡密钥读不到、模块来源读不到、待更新读不到）也未逐一覆盖。

### U7 库文件本身零直接夹具

`scripts/linux/dbk.sh`（总控分发）、`dbk-cli.sh`、`dbk-obs.sh`、`dbk-log.sh`、`dbk-head.sh`、`scripts/windows/dbk-cli.ps1`、`dbk-obs.ps1` 只被步骤脚本间接覆盖（按 basename 在 case 文件里的出现情况判定）。`dbk.sh` 的分发只在 `windows/case-cli-contract.sh` 的 C1 对 `dbk.ps1` 有对应物，Linux 侧无等价用例。

## 五、门禁盲区（违规但绿灯，均已实证）

### 5.1 check-docs.sh

控制组 Run A（干净副本 `/tmp/fx/gate`，仅加一个**会被扫描**的 `docs/zzz-control.md`）：
```bash
bash scripts/repo/check-docs.sh
ERROR docs/zzz-control.md:3 C5 卡编号引用无法解析: 01-99
ERROR docs/zzz-control.md:4 C8 emoji
check-docs: FAIL (2 个问题)        # 耗时 3m30s
```
文件里还有：第 5 行 ⭐（U+2B50，UTF-8 `E2 AD 90`）、第 6 行 `[坏](nope.png)` 与 `[坏2](nope.yml)` —— **一个都没报**。

Run B（把同一份文件挪到 `docs/design/`，再往 `checklists/deploy.md` 加 ⭐ 与 `[坏](nope.png)`，再建 `scripts/linux/sub/loose.sh`）：
```bash
bash scripts/repo/check-docs.sh   →  check-docs: OK     # 耗时 3m33s
```

| 编号 | 位置 | 违规 | 后果 |
|---|---|---|---|
| D1 | `scripts/repo/check-docs-lib.sh:85` `default_docs()` 只 `find "$ROOT/docs" -maxdepth 1` | `docs/design/zzz-control.md` 里放 `-> 01-99`（C5）、emoji、坏链 | 子目录文档（`docs/design/`、`docs/superpowers/`…）**完全不过门禁**；新增/改坏设计文档绿灯 |
| D2 | `check-docs-lib.sh:12` `EMOJI=` 只覆盖 `F0 9F`/`E2 98-9E` | ⭐(`E2 AD 90`)、⌛(`E2 8C 9B`)等大量符号 | 这些 emoji 的 C8 不报（`😀` 在同一文件里能报，说明不是检测器整体失效） |
| D3 | `check-docs.sh:42` `grep -E '\.(md|sh|ps1|txt|snippet|conf)$'` | `[坏](nope.png)`、`[坏2](nope.yml)`、指向目录/无扩展名的坏链 | 图片与其它扩展名的死链不报 |
| D4 | `check-docs-repo.sh:18` `for f in "$ROOT/scripts/$d"/*.sh …`（非递归） | `scripts/linux/sub/loose.sh`：无 `# 对应卡:` 头、不被任何卡引用、不在 `steps.tsv` | C9b/C9c（及 C9d 的"本侧步骤脚本"集合）**看不到子目录里的步骤脚本** |

最小修法：`default_docs` 去掉 `-maxdepth 1` 或显式加 `docs/design`；`EMOJI` 改成正则覆盖 `\xE2[\x80-\xBF]` 与 `\xF0\x9F`（或对非 ASCII 符号单独规则）；链接检查改为"任意相对链接目标必须存在"（至少加 png/jpg/yaml/yml/json）；`check-docs-repo.sh` 的脚本集合改用 `find "$ROOT/scripts/$d" -name '*.sh' -o -name '*.ps1'`。

### 5.2 check-scripts.sh

同一副本里加两处违规后：
```bash
bash scripts/repo/check-scripts.sh   →  check-scripts: OK
```
- **行数上限漏报**：`scripts/linux/zzlong.sh` —— `wc -l` = 200、`awk 'END{print NR}'` = 201（末行无换行）→ `check-scripts.sh:41` 的 `if [ "$n" -gt 200 ]` 不触发。这跟 check-docs 已经修过的 F4b（C4 少算 1 行）是同一类 bug。
- **S-1 漏项**：`scripts/linux/zz-yum.sh` 里三条装包命令（分别调 yum、zypper、pacman）→ `check-scripts.sh:16` 的 `S1_PAT='…apt…|aptitude|dpkg|dnf|snap(d)?|rpm-ostreed?'` 不含 yum/zypper/pacman/apk → 不报 `S1_PKG_LEAK`。
- 次要：`check-scripts.sh:27` 的 S-2 只在 `git rev-parse --git-dir` 成功时跑（非 git 树静默跳过，注释已声明），且只看 `git ls-files` 的**追踪**文件 —— 未追踪文件的空格名/散落仓库根不会被拦（这正好是 S-2 想防的那类事故）。

最小修法：行数用 `awk 'END{print NR}'`（或补齐尾换行后 `wc -l`）；`S1_PAT` 补 `yum|zypper|pacman|apk|flatpak`；S-2 用 `find` 补充未追踪文件。

### 5.3 门禁运行成本（顺带记录）

`check-docs.sh` 默认全仓跑一次 3m30s、`check-docs-repo.sh` 单跑 59s、`check-scripts.sh` 1m39s、`check-docs` 夹具全套 >14m（`extra-checks-c9.sh` 的 F12a 要跑两次全仓 repo 模式）。慢的根因是 MSYS 下的子进程开销（几乎全是 `grep`/`sed`/`awk` 逐文件起进程）。这不是正确性问题，但会让"每次提交都跑门禁"变得不现实。
