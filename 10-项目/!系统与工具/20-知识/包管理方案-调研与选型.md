# 包管理方案:全网调研与本机选型(2026-09)

> 前提:本机(ELEVEN237038 / Win11 25H2)同时存在 **5 个软件来源**,且此前"禁用 winget、scoop 只留 SDK"的规则本次**全部作废重来**,重新评估。
> 结论先行:**没有一个现成方案能同时解决"统一真源 + 漂移检测 + PATH 治理"**;建议自建一个**薄编排层**(复用现有管理器,不重造安装器),MVP 只做**只读盘点与漂移检测**。
> 调研方法:全部结论回溯到一手来源(官方文档 / 源码 / 仓库实时数据),仓库数据用 `gh api` 现取(2026-09-30)。

## 一、本机软件全景(实测)

| 来源 | 数量 | 安装位置/作用域 | 是否需要 UAC | 备注 |
|---|---|---|---|---|
| **scoop** | 17 | `~\scoop`,用户级 | 否 | 7zip、bat、cacert、dark、fd、gh、helix、jq、latex、make、pwsh、python、ripgrep、scoop-search、shellcheck、temurin21-jdk、wget |
| **Chocolatey** | 3 | 各自标准位置,机器级 | 是 | Cmder、pandoc、wireshark |
| **winget 可见** | **78** | 混合(机器级为主) | 视包而定 | 含大量系统运行库(VCRedist/.NET/VCLibs/ODBC/OLEDB)与真应用(Git、Docker Desktop、IDEA、JDK 26、VS Code、Edge、Ditto、Bandizip、PDF24、OBS、PotPlayer、Zed、QQ、微信、网盘、输入法…) |
| **Microsoft Store(Appx)** | 65 | 系统管理 | 否 | 含系统组件与 OEM(Dell/Dolby/Intel/Kaspersky ShellEx) |
| **手工安装(仅注册表)** | ~40 | 混合 | 是 | Chrome、Office 2021、Dell 全家、卡巴斯基、Android Studio、SSMS、VS Build Tools、Node.js、Xshell、游戏等 |
| **语言工具链** | — | — | — | node(手工 MSI)、python(scoop)、pip(scoop python 自带)、pnpm/npm 全局包、rustup(手工)、cargo、JDK 21(scoop)+ JDK 26(Oracle 手工) |

### 由此暴露的五个真实问题(均有本机实证)

1. **同一软件多份安装** → 命令解析不确定。实证:MiKTeX 曾被 scoop 与 choco 各装一份(已删其一);Node.js 是手工 MSI 而 scoop 侧也能装 `nodejs-lts`。
2. **更新来源碎片化**:UniGetUI 一处、应用自带更新器一处、手动一处。实证:winget 后端关闭后,78 个包瞬间失去统一更新入口。
3. **没有可复现的清单真源**:换机/重装无法一键还原(scoop/choco/winget 各自能 `export`,但没有统一真源,也没有"谁负责哪个包"的声明)。
4. **没有漂移检测**:装了哪些、归谁管、是否落后,没有单一视图。实测 `winget list` 里同时存在"已装版本 + 可用版本 + 来源",但这只是 winget 一家的视角。
5. **PATH 顺序无人治理**。机制事实:Windows 的 PATH = **Machine 优先 + User 追加**;shim 与 MSI 安装混用时互相遮蔽。行业里已出现专门诊断工具(`whichway`)与真实事故(某 agent 安装器把自带 node 强插到 User PATH 最前,持续覆盖用户选择)。

## 二、调研:四类候选方案

### A. Windows 系统级包管理器

| 项目 | 解决的问题 | 架构 | 技术依赖 | 活跃度(2026-09-30 实测) |
|---|---|---|---|---|
| **winget**(microsoft/winget-cli) | 官方、目录最大、系统自带 | YAML manifest + COM API + REST 源;`winget export` 可导出清单 | App Installer / Windows | **26467 stars C++ MIT,2026-09-30 推送** |
| **Chocolatey**(chocolatey/choco) | 企业级、脚本化、私有源 | nuspec + **PowerShell 安装脚本**(自由度高) | .NET + PowerShell | **11528 stars C# 许可 NOASSERTION(免费版受限),2026-09-25** |
| **Scoop**(ScoopInstaller/Scoop) | 用户级、无 UAC、便携 CLI | **git 仓库 JSON manifest + shim**,bucket 分治 | PowerShell + git | **24707 stars 许可 NOASSERTION,2026-09-30** |
| **MSYS2/pacman** | Unix 工具链与依赖解析 | pacman + 自有 POSIX 运行时 | MSYS2 运行时 | 976 stars(installer 仓),2026-09-27 |
| **Nix**(NixOS/nix + nix-community/NixOS-WSL) | 可复现、原子回滚 | 内容寻址存储 + 派生(derivation) | **Windows 上依赖 WSL2**(官方只支持 Linux/macOS);原生 Windows 仍是实验 | 17803 stars LGPL-2.1,2026-09-28 |

**可复用**:winget 的 manifest 模型与 `export`;Chocolatey 的包脚本生态;Scoop 的 **manifest + shim**(轻、可审、用户级);Nix 的 **store + generation 回滚**与声明式思路;MSYS2 的依赖解析。
**要避开**:Chocolatey 免费版的功能限制与"安装脚本即执行任意代码"的攻击面;Scoop 只管用户级且依赖 git;**Nix 原生 Windows 尚未成熟**(官方支持仍以 WSL2 为主),与 Windows 软件生态脱节。

### B. 统一层与更新编排

| 项目 | 解决的问题 | 架构 | 技术依赖 | 活跃度 |
|---|---|---|---|---|
| **UniGetUI**(Devolutions/UniGetUI,原 WingetUI) | 一个界面管 10 个后端 | **后端抽象 `IPackageManager` + 操作队列/重试/状态机**;`PEInterface` 注册 WinGet/Scoop/Chocolatey/Pip/Npm/DotNet/PowerShellGallery/Vcpkg/Cargo/PowerShell7 | .NET 10 + WinUI 3,约 40 个子项目 | **26338 stars C# MIT,2026-09-30** |
| **Topgrade**(topgrade-rs/topgrade) | 一条命令更新所有工具 | **检测已装工具 → 依次调用各管理器**;支持自定义命令插槽 | Rust | **4609 stars Rust GPL-3.0,2026-09-29** |
| **winget configure + DSC v3** | 声明式、幂等配置机器 | YAML 配置 + DSC v3 资源(**Get/Set/Test 三段式**,可重复执行)+ Assertions 前置断言 | winget ≥ 1.11 + `Microsoft.DesiredStateConfiguration` 包 | DSC 活跃;配套 GUI `microsoft/winget-studio` 仅 67 stars |
| **chezmoi / Devbox** | dotfiles / 环境即代码 | 状态库 + 差异预览;容器化环境 | Go | 21779 stars MIT / 12378 stars Apache-2.0 |

**可复用**:UniGetUI 的**后端抽象与操作状态机**(本机已在用,可直接读它的设置与操作历史);Topgrade 的**"先检测再调用"编排**;DSC 的**Get/Set/Test 幂等三段式与断言**;chezmoi 的**差异预览工作流**。
**要避开**:Topgrade 是 **GPL-3.0**(可用作外部命令,不可抄代码);UniGetUI 与 Topgrade **都没有声明式真源、没有漂移检测**;`winget configure` 把真源绑死在 winget 上,且 DSC v3 资源生态还年轻。

### C. 运行时/工具链版本管理(与系统包管理器的边界)

| 项目 | 解决的问题 | 架构 | 活跃度 |
|---|---|---|---|
| **mise**(jdx/mise) | 多语言运行时版本,按项目切换 | **shim + `.tool-versions`/`.nvmrc` 解析**;`activate_aggressive` 可把工具前置到 PATH 以压过竞争者 | **34464 stars Rust MIT,2026-09-30** |
| **proto**(moonrepo) | 同上,偏 monorepo | 工具链管理,声明式优先 | 1428 stars MIT |
| **asdf** | 同上(插件生态老牌) | Go 重写后为 0.16+ | 25589 stars MIT |
| **uv**(astral-sh/uv) | Python 环境/依赖 | Rust 单二进制 | **90315 stars Apache-2.0** |
| **rustup** | Rust 工具链 | 官方 | 7053 stars Apache-2.0 |
| **pnpm / cargo-binstall** | Node 依赖 / Rust 预编译二进制 | — | 36715 stars MIT / 2900 stars GPL-3.0 |

**可复用**:shim + **按项目声明版本**;mise 对 PATH 遮蔽问题的显式处理(它专门有 `activate_aggressive` 与排障文档)。
**要避开**:同一运行时**既由系统包管理器装、又由版本管理器装**(本机正是这种状态:node 手工 MSI + scoop 也能装)→ 必然遮蔽与版本错乱。边界应显式声明:**运行时由版本管理器负责,CLI 工具由系统包管理器负责**。

### D. 共性设计结论(所有方案都踩过的坑)

| 设计 | 为什么值得复用/避开 |
|---|---|
| **复用现成管理器的下载/校验/卸载** | 自己实现下载+校验+解压+卸载 = 重复劳动且安全面大 |
| **Get/Set/Test 幂等三段式**(DSC) | 让"应用配置"可重复执行,天然支持漂移检测 |
| **先检测再调用**(Topgrade) | 未安装的管理器不应被调用;本机正好有 10 个后端 |
| **避开:无回滚的批量升级** | 一次 `update all` 失败无法定位与撤销 |
| **避开:混用用户级/机器级而不声明** | Windows PATH 是 Machine 优先 + User 追加,顺序必须显式治理 |
| **避开:GUI 作为唯一入口** | 不可脚本化、不可版本化、不可自动化验证 |

## 三、结合本机需求的选型

### 结论:自建**薄编排层**(不重造安装器)

理由:本机的三个核心痛点(统一真源、漂移检测、PATH 治理)**没有任何现成工具覆盖**;而"下载与安装"这件事已经有三套成熟管理器在做,自建不应重复。

| 层 | 选型 | 理由 |
|---|---|---|
| 语言 | **Rust**(单二进制、无运行时、Windows 友好) | 与本会话已验证可行的技术栈一致;`whichway`/`mise`/`uv` 都用 Rust 做同类工具 |
| 清单真源 | **TOML**(每包声明:期望来源 + 版本策略 + 作用域) | 可版本化、可审、易 diff |
| 状态采集 | 各管理器原生命令(`scoop export`/`choco list`/`winget list`/`pnpm ls -g`/`pip list`/注册表) | 不自建包索引 |
| 执行 | **调用各管理器原生命令** | 复用其下载/校验/卸载;失败可定位到具体管理器 |
| 呈现 | CLI + JSON(可选 TUI) | 可脚本化、可自动化验证 |
| 许可 | 自身 MIT/Apache-2.0;**依赖只取宽松许可** | 避开 Topgrade(GPL-3.0)与 cargo-binstall(GPL-3.0)的代码 |

### 系统架构(五层,单向依赖)

1. **采集层**:后端适配器(scoop / choco / winget / pnpm / pip / Store / 注册表)→ 归一化为 `PackageRecord { name, version, source, scope(user|machine), install_path, has_update }`
2. **清单层**:TOML 真源(`packages.toml`),声明每个包的**期望来源**与**版本策略**;支持多机 profile
3. **决策层(纯函数)**:计算五类漂移 —— **缺失 / 多余 / 版本不符 / 来源不符 / PATH 被遮蔽** → 输出计划(plan)
4. **执行层**:按计划调用各管理器原生命令(幂等;每步可回滚记录);**永不自己下载或安装**
5. **呈现层**:人读报告 + JSON

### MVP 范围(阶段一,**只读**)

采集 + 归一化 + 漂移检测 + PATH 遮蔽诊断 + 报告。**明确不做**:apply/update、GUI、跨机同步、自建包索引。

### 开发顺序(每步可独立验收)

1. **采集层**:7 个后端适配器 + 归一化模型(用本机真实数据做测试)
2. **漂移引擎**:五类差异计算(纯函数,合成数据全覆盖单测)
3. **PATH 诊断**:解析 Machine/User PATH + 各 shim 目录,回答"`node`/`python`/`java` 实际解析到哪个二进制、被谁遮蔽"
4. **报告**:人读 + JSON
5. **清单真源**:TOML 读写 + `plan` 输出(仍只读)
6. *(阶段二)* **apply**:按清单调用管理器,幂等 + 失败即停 + 变更记录
7. *(阶段二)* **update**:编排各管理器升级(先检测已装工具再调用)

## 四、待确认的问题

1. 是否**自建**这个薄编排层?还是先用「UniGetUI + Topgrade + 各自 export」的现成组合顶着(覆盖更新与清单,但没有统一真源与漂移视图)?
2. 语言 **Rust** 是否认可?
3. **MVP 只做只读盘点**是否可接受(不做任何安装/卸载/升级)?
4. 边界规则是否按"**运行时归版本管理器、CLI 工具归系统包管理器**"来定?
5. 落位:`F:\0-code\20-active\tool-<名字>`?
