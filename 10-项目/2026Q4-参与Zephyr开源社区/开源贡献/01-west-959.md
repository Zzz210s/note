## 二、改动前的现状(读代码得到)

`west_commands` 实际上是**两套并行结构**:

| 结构 | 位置 | 形态 |
|------|------|------|
| `self.west_commands` | `Project` / `ManifestProject` / `Manifest` | `list[str]`,经 `_west_commands_list()` 规范化 |
| `self._west_commands_manifest_dirs` | `Project` / `ManifestProject` | `dict[str, str]`,命令 → 声明它的 manifest 目录 |

三个模块级 helper 分别承担:构造(`_west_commands_list`)、序列化时"只有一个元素就退化成字符串"(`_west_commands_maybe_delist`)、去重合并(`_west_commands_merge`)。

使用点(共 6 处):

- `commands.py`:`project._west_commands_manifest_dirs.get(cmd)` → 决定扩展命令文件相对哪个根解析
- `Project.__init__` / `ManifestProject.__init__` / `Manifest.__init__`:初始化两个结构
- `Manifest._load_self`:合并当前 manifest 自己的 west-commands
- 导入路径(`_import_project_submanifest` 附近):把子 manifest 的命令路径重定位到项目根,并记录来源目录

## 三、设计决策(与 issue 建议不一致的地方,已在 PR 里说明理由)

| issue 的建议 | 实际做法 | 理由 |
|--------------|----------|------|
| 提升为**类** | `class WestCommands(list[str])` | 同意 |
| 可能是 **dict 子类** | 用 **list 子类** | `west_commands` 是被文档与测试固定为"路径列表"的公开属性;`tests/test_manifest.py` 明确断言 `p1.west_commands == ['p1-commands.yml', 'm1-commands.yml', 'm2-commands.yml']`("resolved in import order")。改成 dict 子类会改变该属性类型,影响扩展作者;list 子类则 `manifest.py` 之外零改动 |
| `_west_commands_merge` → **`__iadd__`** | 用 `merge()` 方法 | `WestCommands` 是 list,`+=` 的既有语义是"追加、允许重复";把它改成去重会让读代码的人误解 |
| `_west_commands_maybe_delist` → **字符串表示** | 用 `as_manifest_value()` | 序列化后的值可能是 `str` **也可能是 list**,`__str__` 只能返回 `str`,表达不了;另外返回值必须是**普通 list**(`yaml.safe_dump()` 无法表示 list 子类) |
| 把 `_west_commands_manifest_dirs` 纳入类 | `manifest_dirs` 成为类的属性 | 同意:两套结构由类统一持有,不再需要手工保持同步 |

## 四、实现要点

- `WestCommands.__init__(west_commands=None, manifest_dirs=None)`:接受 `str | list[str] | WestCommands | None`;从另一个 `WestCommands` 构造时**只复制条目、不复制目录**(保持原行为:项目自己的命令相对项目根解析)
- `add(entry, manifest_dir=None)`:不存在才追加;目录用 `setdefault`(先到先得)
- `merge(other)`:把 other 的条目按"self 在前、新条目按序追加、过滤重复"合并,并带走 other 的目录;接受 `WestCommands` 或原始 `str` / `list`
- `as_manifest_value()`:单条目返回 `str`,否则返回**普通 list**
- 删除 `Project` / `ManifestProject` 上的 `_west_commands_manifest_dirs` 私有属性;`commands.py` 改读 `project.west_commands.manifest_dirs`
- `_import_ctx.manifest_west_commands` 的类型从 `list[str]` 变为 `WestCommands`(就地 `merge`,因为 NamedTuple 字段不能重绑定)

### 第 1 轮 review 的处理(可复用经验)

**Copilot 的发现是对的**。旧代码在 `_load_self()` 里先做真值判断,所以 `west-commands: ''` 被视为"没有 west 命令";我的重构把 `WestCommands(west_commands)` 提到了判断之外,空字符串变成了条目 `''`。

**验证方法(值得记住)**:用一个临时 worktree 检出 `upstream/main`,再用 `PYTHONPATH` 指向它的 `src` 跑同一段脚本,直接对比新旧行为:

```bash
cd <仓库>
git worktree add -q ../west-baseline upstream/main
PYTHONPATH="F:/0-code/20-active/west-baseline/src" uv run python -c "..."
git worktree remove ../west-baseline --force
```

结果:基线 `west_commands == []`,我的版本 `== ['']` → 确认回归。

**修法**:把合并放回原来的真值判断里(保持旧行为),并加回归测试 `test_west_commands_falsey_value_in_self_is_ignored`。改完 359 passed。

**同时澄清的两点**(写进了 PR 评论):

- *project* 级别的 `west-commands: ''` 行为**未变**:旧代码 `_west_commands_list('')` 同样返回 `['']`,`as_dict()` 同样输出 `''`
- 关于"list 变异会绕过元数据":`append()` 之类无法记录 manifest 目录,但这**不是静默错误** —— 没有目录的条目本来就相对项目根解析;删除条目只会在 `manifest_dirs` 里留一条不可达记录,而查询由列表驱动,取不到它。要做到元数据不可绕过只能用组合代替继承,那会改变公开属性的类型,是本 PR 刻意避免的

**教训**:重构中把"真值判断"这类隐式契约挪位置时,必须先对照基线验证;只看测试通过是不够的 —— 既有测试没覆盖 `''` 这个输入。

读完 PR #920 的评审口味后自查发现:`WestCommands.__init__(manifest_dirs=...)` 这个参数**生产代码零调用点**,只有测试在用。按 marc-hb 在 #920 里"为只用两处的内部函数新增参数签名是 overkill"的态度,应当删掉。已删除并用 `add()` 重建测试夹具(`cf03d9e`,+177/-62)。
