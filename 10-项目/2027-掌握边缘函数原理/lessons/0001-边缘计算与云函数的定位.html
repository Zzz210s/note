边缘函数到底解决了什么问题

这节课的胜利:用一条命令问出你的请求被哪个边缘节点处理了(实测:LAX / US), 再写出一张 6 维对比表说清"边缘函数 vs 云函数"的取舍,并指出你的哪一类需求适合它。

为什么是这一步

使命说这是职业目标的核心项目:要能解释"代码为什么能在离用户最近的节点上跑起来"。 但如果不先分清它和云函数的差别,后面所有原理(隔离模型、冷启动、CDN 分发)都无处挂靠。

最小知识:三条

  1. 云函数跑在"几个区域",边缘函数跑在"几百个节点"。 同一个函数被部署到全球边缘节点,用户请求由最近的那个节点执行 —— 省掉的是"用户到区域机房"的往返。
  2. 代价是"手脚被绑住"。边缘侧资源严格受限:CPU 时间有上限、内存几十 MB 级、代码包有体积限制、 不能开长期后台线程、不能跑任意二进制。所以它擅长"轻、短、快"的逻辑,不擅长重计算与有状态长连接。
  3. 收益是"距离 + 弹性"。就近执行降低延迟;而"每个请求一个隔离实例"的模型让冷启动必须极快 —— 这就引出下一节的隔离模型(Isolate vs 容器 vs Wasm)。

动手:问出你的请求落在哪个节点

Cloudflare 提供了一个自检端点,直接告诉你答案(实测输出来自你这台机器):

curl -s https://www.cloudflare.com/cdn-cgi/trace | grep -E "^(colo|loc|ip|tls|http)="
# colo=LAX      ← 处理你请求的边缘节点:洛杉矶
# loc=US        ← 你的出口 IP 被识别为美国
# ip=45.43.58.176
# tls=TLSv1.3
# http=http/1.1

先读你自己的数字:你在国内,但 colo=LAX —— 说明你的流量出口在美国(走了代理链路)。这正是"边缘节点选择取决于用户到节点的网络位置"的活例子: 边缘计算优化的不是"服务器有多快",而是"服务器离你多近"。

再量一次"近与远的差别"(实测):

for u in https://www.cloudflare.com/cdn-cgi/trace https://example.com; do
  printf "%-46s " "$u"
  curl -s -o /dev/null -w "connect=%{time_connect}s total=%{time_total}s\n" -m 20 "$u"
done
# Cloudflare 边缘:connect=0.0079s total=0.832s
# example.com:     connect=0.0189s total=2.112s

自测(选项一样长,别从长度上猜)

1. 边缘函数优化的核心是什么?

对。它买的是"距离"(省掉用户到区域机房的往返),不是单机算力。体积小、启动快都是为这个目标服务的手段。

2. 下列哪件事最不适合放在边缘函数里?

对。边缘侧有 CPU 时间与内存上限,长任务会被直接掐断;重计算应该放回区域或专用算力。其余三项都是边缘函数的典型用法。

3. colo=LAX 说明了什么?

对。colo 是"处理这次请求的边缘节点代码"。你的出口 IP 被判为美国,所以就近选了 LAX —— 这正说明节点选择看的是你到节点的网络位置。
