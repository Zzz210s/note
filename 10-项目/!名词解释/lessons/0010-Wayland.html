Wayland:谁在画,谁在显示

这节课的胜利:说清 X11 与 Wayland 的分工差别 —— 客户端发请求让服务端画,还是客户端自己画、合成器只负责合成与显示 —— 并当场明白为什么截图、录屏、全局快捷键、远程桌面这四类工具在 Wayland 下几乎都要换一套。 本机 WSLg 就是一个活的 Wayland 实现,我们读它的合成器日志与套接字来验证。

一句话定位

Wayland 只是一份协议:合成器把输入事件发给客户端,客户端在本地渲染,再把显存缓冲区与更新信息交回合成器 (Wayland FAQ)。 X11 里多了一层:客户端把渲染请求交给 X 服务端,X 服务端编程硬件、管前缓冲,还要替客户端判断"这次点击该给谁" —— 可它并不知道合成器把窗口缩放旋转过,所以判断常常是错的 (Wayland: Architecture)。 一句话判定:问「谁在画窗口内容、谁在管输入与显示」。Arch Wiki 第一句点得很清楚: 「Wayland 只是协议,不像 Xorg 那样有一个统一的显示服务器可以装」 (Arch Wiki: Wayland)。

为解什么痛点而生

X11:中间人夹在客户端与合成器之间

痛点:内核已经有 KMS 与 evdev,库也有了 mesa / cairo / Qt,可 X 服务端仍要替所有人管输入、管前缓冲、管显示模式; 合成器要显示自己合出来的画面,还得再经过 X 服务端一次 —— 每一帧多几次上下文切换,而且它算不对窗口坐标。 定义:X11 里 X 服务端是显示服务器,客户端通过它画、也通过它收事件。 大白话:大厅里站着一个总管,谁要画画都得先跟他说;连放映员(合成器)想放画面也得经过他。

Wayland:谁的程序谁自己画

痛点:这一层中间人是历史包袱 —— 上面说的那些活,内核与库都已经能干了。 定义:合成器直接接管 KMS 与输入设备,内置就是显示服务器;客户端渲染进共享缓冲区,只通知"哪块更新了",合成器合成后直接排一次翻页。 大白话:把总管撤了,放映员直接管设备;每个程序自己画好交上来。顺带一个副作用: 客户端读不到别人的缓冲区了 —— 以前"谁都能抓屏、抓键盘"的自由没了,换来的是"想录屏 / 记键盘得先申请"。

课里才有:本机 WSLg 就是一个活的 Wayland 实现(2026-09-26 现跑)

Windows 上跑 Linux 图形程序靠 WSLg。它不是魔改 X11,而是在 WSL 里跑一个 Wayland 合成器,再把画面用 RDP 送回 Windows(Microsoft Learn: Run Linux GUI apps with WSL)。 读一眼合成器的启动命令,三件事一次说完: 

$ wsl.exe -e bash -lc "ls /mnt/wslg"
distro  doc  pulseaudio.log  PulseAudioRDPSink  PulseAudioRDPSource  PulseServer
run  runtime-dir  stderr.log  versions.txt  weston.log  wlog.log

$ wsl.exe -e bash -lc "head -6 /mnt/wslg/weston.log"
Date: 2026-09-26 CST
[17:22:33.030] weston 9.0.0
               https://wayland.freedesktop.org
[17:22:33.030] Command line: /usr/bin/weston --backend=rdp-backend.so --modules=wslgd-notify.so --xwayland --socket=wayland-0 --shell=rdprail-shell.so

--socket=wayland-0 是 Wayland 协议通道,--xwayland 给只认 X11 的老程序留了兼容层, --backend=rdp-backend.so 是画面出口(合成结果用 RDP 送回 Windows);versions.txt 记的是 WSLg 1.0.71、weston 9.0.0、mesa 与 pulseaudio 各自构建号。

再看这条通道究竟是什么东西 —— 这也是"Wayland 为什么不支持远程"的物理原因: 

$ wsl.exe -e bash -lc "ls -l /run/user/0/wayland-0; ss -xl | grep wayland; ss -tln | grep -c ':6000 '"
lrwxrwxrwx 1 root root 31 Sep 26 17:23 /run/user/0/wayland-0 -> /mnt/wslg/runtime-dir/wayland-0
u_str LISTEN 0 128 /mnt/wslg/runtime-dir/wayland-0 16391 * 0
0

$ wsl.exe -e bash -lc "echo \$XDG_SESSION_TYPE; echo \$WAYLAND_DISPLAY; echo \$DISPLAY; ls /usr/share/wayland-sessions"
                                    # XDG_SESSION_TYPE:空
wayland-0
:0
                                    # 会话清单:空

Wayland 的通道是一个 unix 域套接字(u_str,文件系统里的一根管子),不是网络端口; X11 这边默认连 TCP 6000 都没开(grep -c 得 0),但也听在 /tmp/.X11-unix/X0 上 —— 两套通道同时存在,正是「Wayland 主体 + Xwayland 兜底」。 环境变量也对得上:WAYLAND_DISPLAY=wayland-0 与 DISPLAY=:0 并存。 诚实边界:XDG_SESSION_TYPE 是空的(这里不是一次图形登录会话),/usr/share/wayland-sessions 也没有桌面条目; wayland-info / grim / wl-copy 本机都没装,所以这节课不现场演示抓屏 —— 但合成器与套接字是真的。

辨析练习:这一条在两边成立吗?

共 4 例。判定靠一件事实:X11 里服务端管着前缓冲与输入,Wayland 里客户端自己画、合成器算得准坐标。

1. 一个普通程序想直接读整屏像素来做截图。

X 能,W 不:X11 的通用工具就建立在这条上;Wayland 里别人的缓冲区读不到,得经合成器或门户。

2. 程序把窗口内容渲染进自己的缓冲区,再交给负责显示的对方。

X 能,W 能:X11 也有直接渲染这条路;区别在于 Wayland 里这是唯一方式,X11 里还能让服务端替你画。

3. 合成时把窗口缩放、旋转之后,系统仍能算准鼠标落在窗口内的哪个位置。

X 不,W 能:官方架构文档里就是拿这条当 X 的老毛病 —— 服务端不知道合成器做了什么变换,Wayland 的合成器自己维护场景树,会做逆变换。

4. 把另一台机器上运行的图形程序的窗口,显示在你自己这块屏幕上。

X 能,W 不:X 协议天生网络透明(DISPLAY=主机:0);Wayland FAQ 明确写着远程渲染不在协议范围内,要远程就得整桌面搬走。

自测(选项一样长,别从长度上猜)

1. 关于两套架构的分工,哪句对?

对,这是 Wayland 的分工。本机 weston 的命令行就是证据:--socket=wayland-0 收客户端缓冲区,--backend=rdp-backend.so 负责显示。

2. 一个录屏工具想在 Wayland 下正常工作,通常要哪一条?

对。缓冲区是私有的,录屏得经 ScreenCast 门户拿一条流(底层常是 PipeWire),再由编码器处理。

3. 本机 weston 的启动参数同时说明了哪三件事?

对:--socket=wayland-0 + --xwayland + --backend=rdp-backend.so,正好是"Wayland 主体 + 老程序兜底 + 把画面送回 Windows"。
