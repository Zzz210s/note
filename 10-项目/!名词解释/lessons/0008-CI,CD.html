CI/CD:从「推送就自动检查」到「通过就自动上线」

你能做到:说出 CI / 持续交付 / 持续部署三层到底差在哪一步(答案:差在「有没有人按一下」), 并说清持续部署之前必须先备好什么。往后再听到「等 CI 绿了再合并」「CD 还没配」,你立刻知道各自在讲哪一层。

1 | 定义

CI(持续集成)是一个规矩:每个人频繁把改动合进同一条主线,而每一次合并都由自动化构建与测试验证 (Fowler: Continuous Integration)。 持续交付在检查通过后自动打包成随时可发布,但上不上线由人决定。 持续部署再往前一步:验证通过就自动进生产,没有人工确认 (Fowler: Continuous Delivery)。

大白话:CI 管「合得进、跑得通」,持续交付管「随时能发」,持续部署管「自动去发」。

2 | 解决的痛点

各改各的,谁也不知道对方的改动会不会把自己弄崩。一直攒到发布那天才把几周的分支合到一起,冲突和故障一起爆出来 —— 这种场面叫集成地狱。

检查自动化了,发布却没有:手工打包、手工填参数、手工传服务器。每次步骤都不一样,发版还得挑日子。

发布窗口本身也在花成本:攒批发布、挑低峰上线、上线后盯半小时,全是用人的时间换「少出事」。

3 | 心智模型

我推一次代码 → 自动化检查:构建、测试、静态检查 → 打包成随时可发布 → 人工确认那一下 → 自动进生产 → 线上多了一个新版本

三层是递进,不是三个并列的产品:上一层是下一层的地基,挪掉地基就没得谈。

链条末尾那段还有自己的套娃:一份剧本(何时跑) 里装 一幕(在哪台机器上跑), 一幕里装 一句句台词(一条命令)。理解这三层,任何平台的配置文件都读得下来。

4 | 类比与边界

类比:像坐飞机。安检是检查 —— 每次进门都过一遍;登机口是上线 —— 过了这道才真的走。

这个类比会在三处骗你:

  • ① 安检过了不等于登机。检查绿了只是「这一关过了」;后面还有没有部署那一步,是另一件事。
  • ② 传送带不会报告「它漏了」。检查只证明配置里写的那几项过了,没写的它一概不管。
  • ③ 类比里没有「收回来」这个动作。行李上了飞机就回不去,而软件上错了必须能一键退回上一版 —— 这是持续部署的第一护具。

5 | 它怎么工作

  1. 先有一个触发条件。推送、合并请求、打标签或定时,任一发生就启动一趟。
  2. 跑在一台干净的临时机器上。从零拉代码、装环境、跑完即销毁 —— 所以「在我机器上是好的」这句话在这里不成立。
  3. 按台词一句句来。一句是一行命令,或一个可复用的动作;前一句失败,后面就停下。
  4. 判红绿看退出码。程序跑完回一个数字:0 是过,非 0 是不过 (Wikipedia: Exit status)。所以把一条手动命令搬进流水线,通常不用改代码,只要它能在干净机器上跑起来(0006 · 巡检器)。
  5. 一幕可以依赖另一幕。检查全绿了,部署那一幕才轮到上场。
  6. 最后一幕挂不挂批准,就是两个 CD 的分界。挂上「必须人工批准」= 持续交付;不挂 = 持续部署。
on: push                     # 什么时候跑:推送到主线
jobs:
  check:                     # 第一幕 = CI
    runs-on: ubuntu-latest   # 一台干净机器,跑完即销毁
    steps:
      - run: npm ci          # 装依赖;失败就整幕红
      - run: npm test        # 跑测试(退出码非 0 即红)
  deploy:                    # 第二幕 = CD
    needs: check             # 检查绿了才轮到它
    steps:
      - run: ./deploy.sh     # 挂人工批准 = 交付;不挂 = 部署

上面这份骨架里的 npm 是包管理器,负责把依赖按锁文件装成一份确定的清单(0004 · Node.js / npm / pnpm)。

6 | 相近名词一句话判定

只问一句:每次推送之后,自动发生的事到哪一步为止?

名词一句话判定(看到这个就是它)它的失效场景
持续集成(CI)自动化只到检查为止,没有任何发布动作只在功能分支上跑自动构建 = 半集成,不是 CI
持续交付自动化到随时可发布,最后那一下留给人按需要外部审批或固定窗口期时,自动化只能到「准备好」
持续部署验证通过后自动进生产,没人按按钮回滚、监控、开关没到位时,它是风险而不是效率
半集成自动构建跑了,但大家并不频繁合进主线问题仍然攒到发布那天才一起爆
部署工具或平台钩子把产物送上线的那一下动作本身人敲它就是手动发布;写进流水线才叫 CD

持续部署的前提(缺一条,自动上线就只是自动出事):

  • ① 检查本身可靠:拦不住问题的检查,只会把问题自动送进生产。
  • ② 能一键回滚:发得出去,也要收得回来。
  • ③ 有特性开关:代码先上线、功能后打开,把「部署」和「发布」拆成两件事。
  • ④ 有监控与告警:自动上线的前提是能自动发现「上线之后坏了」。
  • ⑤ 数据迁移能前后兼容:新旧两版会同时存在几分钟,迁移不能只朝一个方向走。

7 | 常见误解

  • 「CI 就是跑测试」:测试只是其中一步。构建、静态检查、依赖审计、密钥扫描都算 —— 它管的是「这次合并有没有把主线弄坏」。
  • 「有 CI 就有 CD」:流水线里没有发布动作,那就止步于检查;两个 CD 之间还差一次人工确认。
  • 「绿了就说明已经上线」:绿只证明配置里那几项过了,和线上有没有换版是两件事。

8 | 什么时候别用它

  • 一个人一台机器的小脚本:收益很小 —— 不过成本也小,想加随时可以加。
  • 没有回滚与监控时:别上持续部署。先备齐护具,再谈自动化那一步。
  • 发布受外部审批或窗口期约束:自动化只能做到「随时可发」,那一下必须留给人。
  • 检查本身慢到没人愿意等:先修检查,再叠流水线的层数 —— 慢的门禁会被绕过。

10 | 交互练习

辨析练习(4 例):这是哪一层?

选择范围:持续集成 / 持续交付 / 持续部署 / 都不算数。

1. 合并后自动跑测试,检查全过并打好了包,但上线要点一下按钮。

持续交付:自动到了「随时可发布」,最后那一下留给人 —— 那一步正是两个 CD 的分界。

2. 每次推送后云端机器自动重跑构建与测试,没有任何发布动作。

持续集成:自动化到「检查」为止。有 CI 不等于有 CD —— 这层的出口只是网页上一行红或绿。

3. 全部检查通过后几分钟内,线上自动换成了新版本,没人点过按钮。

持续部署:交付那一步的人工确认也被去掉了。代价是回滚与监控必须够硬。

4. 只在功能分支上跑自动构建,主线一天才合一次代码。

都不算数:按 Fowler 这叫半集成。CI 的关键那条是「每个人都往主线推,每次推都触发构建」。

自测(3 题):选一个正确答案

每题只有一个正确选项;选完立刻看到解释。

1. 持续交付与持续部署之间,到底差哪一步?

对。两个 CD 只差「人工确认」:留着是人按,去掉是机器按。其余三项是两层共用的前提,不是分界。

2. 想做到持续部署,最先该补齐的是哪一条?

对。自动发得出去,也要能自动收回来 —— 回滚是第一护具,再配开关、监控与能兼容的迁移。 跑得快、检查全当然重要,但它们是上一层的事。

3. 流水线全绿,但线上还是旧版本,说明什么?

对。绿只证明检查过了;线上没变,说明没有部署那一步,或部署前留了人工确认 —— 这正是持续交付的常态。
