CI/CD:从「推送自动检查」到「通过自动上线」

这节课的胜利:说清 CI / 持续交付 / 持续部署三层到底差在哪一步(答案:差在「有没有人按一下」), 亲眼读一次真实运行记录,并知道 CD 在本机的出口长什么样。读完你再看「等 CI 绿了再合并」「CD 还没配」这两句话,就知道各自在说哪一层。

一句话定位

三层递进:CI 是「频繁合进主线 + 每次合并都自动构建与测试」(Fowler: Continuous Integration); 持续交付在 CI 通过后自动打包成随时可发布,但上不上线由人决定; 持续部署再进一步,验证通过就自动进入生产,没有人工确认 (Fowler: Continuous Delivery · Wikipedia: Continuous deployment)。 缩写有歧义:CD 同时指 delivery 与 deployment —— 听到 CD 先问是哪个 D。

为解什么痛点而生

CI:攒着的分支,合起来会炸

痛点:多人各改各的,直到发布那天才把几周的分支合到一起,冲突与 bug 一起爆发(集成地狱)。 定义:CI 要求频繁集成(Fowler 引 Kent Beck:「代码不要超过几个小时还没被集成」),并用自动化构建验证每次集成。 大白话:与其等着一起体检,不如每天量一次血压 —— 出问题的窗口从「两周」压到「一次提交」。 注意一个常见混淆:只在功能分支上跑自动构建只是半集成,不是 CI。

CD:CI 绿了,发布还在靠人手工搬

痛点:检查自动了,发布没有 —— 手工打包、手工填参数、手工传服务器,每次步骤都不一样,发版还得挑日子。 定义:持续交付把「随时可发布」也自动化,把最后那一下留给人;持续部署把那一下也交给机器。 大白话:交付是「车随时能开,钥匙在人手上」;部署是「钥匙也交给机器,过了就发」。 两个 CD 只差一步,那一步叫人工确认 —— 差别不在技术难度,而在团队对失败的处理能力。

课里才有①:读一次真实的运行记录(全是检查,没有部署)

本机另一个仓库 Zzz210s/ai-session-hub 真接了 CI。下面是 2026-09-25 现跑 gh run list 的原始输出(时间倒序):

$ gh run list -R Zzz210s/ai-session-hub --limit 5
completed  success  test: 删除相关用例改为平台无关(修 CI 在 Linux 上失败)  test  master  push 35519548484  10s
completed  failure  chore: package.json 关键词补全(CRLF 导致上次未生效)        test  master  push 35519431229  11s
completed  failure  fix: 补入被误忽略的 src/live/(克隆后无法运行)+ 关键词      test  master  push 35519243094   8s
completed  failure  chore: 加入 CI、版本 0.5.0、描述与关键词更新               test  master  push 35519029229  10s

这四行就是 CI 的全部意义:连续三次红,改到第四次绿。每次 git push 之后 8~11 秒,一台云端机器重跑同一套检查并留下记录 —— 人不在场,也不用记得跑。 留意 workflow 那一列叫 test:四条记录全是检查,没有一步是部署 —— 这就是「有 CI 不等于有 CD」的本机样本。那个仓库的 workflow 一共三件事,每件都是「人本来要手动做的事」:

阶段命令手动版本就是
单元测试node --test test/*.test.js自己在本地敲一遍
shell 语法检查bash -n setup.sh自己记得检查一遍脚本语法
误提交检查grep -rnE "C:\\Users\\..." .人肉翻自己有没有把家目录路径提交上去

它的注释里写着一条诚实的边界:Windows 专属能力(UIA 标签聚焦、系统回收站、ConPTY)在 CI 里覆盖不到,只能靠本机验证。 所以 CI 覆盖的是「换台 Linux 机器也能跑的那一半」—— 不是全部。

课里才有②:CD 的出口,在本机是部署 CLI

CI 的出口是「网页上一行绿或红」,CD 的出口是「线上多了一个新版本」。本机没有接 CD 的仓库: 2026-09-25 实测本地只有两个 workflow(ai-session-hub/test.yml 与 config-ai/verify.yml),都只做检查。 所以 CD 在本机的可见形态是部署 CLI(下面两个版本号是刚跑出来的): 

$ npm ls -g --depth=0 | grep -E "vercel|wrangler"
├── vercel@59.26.0
└── wrangler@4.138.0
$ vercel --version
Vercel CLI 59.26.0

这两个工具就是「持续部署」里那一步的手动版:人敲 vercel deploy 或 wrangler deploy,产物才会上线; 把它写进 workflow 的部署 job,那一步就从「人敲」变成「检查通过后自动敲」。 本库 2027-掌握边缘函数原理 · 课程地图 的第 5 节正是「动手:部署你的第一个边缘函数」—— CD 那一步的学习出口就在那里。

对照本库自己的手动检查(CI 里跑的正是它,2026-09-25,--quiet 只打分类计数):

$ cd F:/0-Note/50-资源/工具/vault-check && PYTHONIOENCODING=utf-8 python -B check_vault.py --quiet; echo rc=$?
[A1 断链] 0 处
......                          # 共 13 行分类计数,一律 "0 处"
[A14 索引页一致性] 0 处
结论:PASS / rc=0

给它接 CI 的最小骨架就是「on + jobs + steps」三层各一行; 再往下的部署 job 才是 CD —— 而本库目前没有 .github/workflows/(2026-09-25 实测),两层都还是骨架,不是现状。

对比表:三层差在哪一步

层次自动到什么为止人还要做什么典型现象
持续集成构建 + 测试 + 检查决定合不合、怎么发推送后几十秒出现一条运行记录
持续交付再加:打包成随时可发布按一下发布按钮产物就绪,上线要点一下
持续部署再加:自动进入生产出问题才介入通过后几分钟线上自动换版

持续部署的前提(缺一条,自动上线就只是自动出事):CI 本身可靠、可一键回滚、特性开关、监控告警、数据库迁移可前后兼容 —— 展开见速查卡。

辨析练习:这三层里,是哪一层?

共 4 例。判定靠「自动到哪一步为止」:检查、打包、还是连上线也自动。

1. 合并后自动跑测试,检查全过并打好了包,但上线要点一下按钮。

是持续交付:自动到了「随时可发布」,最后那一下留给人 —— 那一步正是两个 CD 的分界。

2. 每次推送后云端机器自动重跑构建与测试,没有任何发布动作。

是持续集成:自动化到「检查」为止。本机那个仓库就是这种 —— workflow 名叫 test,没有部署 job。

3. 全部检查通过后几分钟内,线上自动换成了新版本,没人点过按钮。

是持续部署:交付那一步的「人工确认」也被去掉了。代价是回滚与监控必须够硬,否则等于自动出事。

4. 只在功能分支上跑自动构建,主线一天才合一次代码。

都不算数:按 Fowler 这叫半集成。CI 的关键那条是「每个人都往主线推,每次推都触发构建」。

自测(选项一样长,别从长度上猜)

1. 持续交付与持续部署之间,到底差哪一步?

对。两个 CD 只差「人工确认」这一步:留着是人按,去掉是机器按。其余三项是两层共用的前提,不是分界。

2. 想做到持续部署,最先该补齐的是哪一条?

对。自动发得出去,也要能自动收回来 —— 回滚是持续部署的第一护具;再配特性开关、监控与可前后兼容的迁移。 流水线快与检查全都很重要,但它们属于 CI 那一层。

3. 流水线全绿,但线上还是旧版本,说明什么?

对。绿只证明检查过了;线上没变说明没有部署 job,或部署前留了人工确认 —— 这正是持续交付的常态,不是故障。
