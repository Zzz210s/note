CI/CD:从「推送自动检查」到「通过自动上线」

这节课的胜利:说清 CI / 持续交付 / 持续部署三层到底差在哪一步(答案:差在「有没有人按一下」), 并说清 CI 覆盖不到什么。往后听到「等 CI 绿了再合并」「CD 还没配」,你能立刻知道各自在说哪一层。

一句话定位

三层递进:CI(持续集成)是「频繁把改动合进主线 + 每次合并都由自动化构建与测试验证」(Fowler: Continuous Integration);持续交付在 CI 通过后自动打包成随时可发布,但上不上线由人决定。 持续部署再进一步,验证通过就自动进入生产,没有人工确认(Fowler: Continuous Delivery · Wikipedia: Continuous deployment);缩写有歧义:CD 同时指 delivery 与 deployment —— 听到 CD 先问是哪个 D。

三层各自解什么痛:痛点 / 定义 / 大白话

CI:攒着的分支,合起来会炸

痛点:多人各改各的,直到发布那天才把几周的分支合到一起,冲突与 bug 一起爆发(集成地狱)。

定义:CI 要求频繁集成,并用自动化构建验证每次集成 —— Fowler 引 Kent Beck 的话:「代码不要超过几个小时还没被集成」。

大白话:与其攒着一起体检,不如每天量一次血压 —— 出问题的窗口从「两周」压到「一次提交」。注意:只在功能分支上跑自动构建只是半集成,不是 CI。

持续交付:CI 绿了,发布还在靠人手工搬

痛点:检查自动了,发布没有 —— 手工打包、手工填参数、手工传服务器, 每次步骤都不一样,发版还得挑日子。

定义:持续交付把「随时可发布」也自动化,产物与发布脚本都备好, 只把最后那一下留给人。

大白话:车随时能开,钥匙在人手上 —— 交付这一步的出口是「点一下就能上线」。

持续部署:把那一下也交给机器

痛点:发布窗口本身也是成本 —— 攒批发布、挑低峰上线、手动盯半小时, 这些都在用人的时间换「少出事」。

定义:持续部署在验证通过后自动把新版本送进生产,没有人工确认 (Wikipedia: Continuous deployment)。

大白话:钥匙也交给机器,过了就发。前提是不能缺:CI 本身可靠、可一键回滚、有特性开关、有监控告警、数据库迁移能前后兼容 —— 缺一条,自动上线就只是自动出事。

对比表:三层差在哪一步

层次自动到什么为止人还要做什么什么时候它不适用
持续集成构建 + 测试 + 检查决定合不合、怎么发只有一台机器、只有一个人开发时,收益小但成本也小
持续交付再加:打包成随时可发布按一下发布按钮发布需要外部审批或窗口期时,自动化只能到「准备好」
持续部署再加:自动进入生产出问题才介入回滚、监控、特性开关没到位时,它是风险而不是效率

两个 CD 只差一步,那一步叫人工确认 —— 差别不在技术难度,而在团队对失败的处理能力(Wikipedia: Feature toggle · Wikipedia: Blue-green deployment)。

它长什么样:一份通用的最小流水线

on:                                    # 什么时候跑
  push: { branches: [main] }           # 推送 main 时
jobs:
  check:                               # 这一幕 = CI:跑检查
    runs-on: ubuntu-latest             # 一台临时机器,跑完即销毁
    steps:
      - uses: actions/checkout@v4      # 把仓库拉下来
      - run: npm ci && npm test        # 装依赖 + 跑测试(退出码非 0 即红)
  deploy:                              # 这一幕 = CD
    needs: check                       # 检查绿了才轮到它
    environment: production            # 挂「必须人工批准」= 持续交付
    steps:
      - run: ./deploy.sh               # 不挂批准 = 持续部署

三层结构是通用的:workflow(一个配置文件 = 一份剧本,由事件触发)、job(一幕,在一台机器上跑的一串步骤)、step(一句台词,一条命令或一个可复用的动作)。判红绿靠的是退出码(Wikipedia: Exit status),所以「把一条本来手动跑的命令搬进流水线」通常不用改代码,只要保证它在干净机器上跑得起来。 字段含义见 GitHub: Workflow syntax,从零上手见 GitHub: Quickstart。

CI 覆盖不到什么

绿只说明「配置里写的那几项过了」,别把它当全量证明。常见的空白有三块: ① 平台专属能力(只在某个系统上存在的界面、设备、图形接口,云端 Linux 机器跑不到); ② 需要真实凭据或外部服务的流程(真下单、真发消息、真付款,通常只做到沙箱); ③ 需要人判断的事(这个改动合不合适、文案读起来对不对)。

常见误解

  • 「CI 就是跑测试」不成立:构建、静态检查、依赖审计、密钥扫描都算 —— 它管的是「这次集成有没有把主线弄坏」。
  • 「有 CI 就有 CD」不成立:流水线里没有发布动作,那就止步于检查; 两个 CD 之间也还差一次人工确认。
  • 「绿了就能发布」不成立:它只覆盖配置里那几项;而且推送一次能跑,不保证线上一定换版 —— 绿与上线之间还隔着「有没有 deploy 这一步」。

辨析练习:这是哪一层?

共 4 例。判定靠「自动到哪一步为止」:检查、打包、还是连上线也自动。

1. 合并后自动跑测试,检查全过并打好了包,但上线要点一下按钮。

是持续交付:自动到了「随时可发布」,最后那一下留给人 —— 那一步正是两个 CD 的分界。

2. 每次推送后云端机器自动重跑构建与测试,没有任何发布动作。

是持续集成:自动化到「检查」为止。有 CI 不等于有 CD —— 这一步的出口只是网页上一行红或绿。

3. 全部检查通过后几分钟内,线上自动换成了新版本,没人点过按钮。

是持续部署:交付那一步的「人工确认」也被去掉了。 代价是回滚与监控必须够硬,否则等于自动出事。

4. 只在功能分支上跑自动构建,主线一天才合一次代码。

都不算数:按 Fowler 这叫半集成。CI 的关键那条是「每个人都往主线推,每次推都触发构建」。

自测(选项一样长,别从长度上猜)

1. 持续交付与持续部署之间,到底差哪一步?

对。两个 CD 只差「人工确认」这一步:留着是人按,去掉是机器按。其余三项是两层共用的前提,不是分界。

2. 想做到持续部署,最先该补齐的是哪一条?

对。自动发得出去,也要能自动收回来 —— 回滚是持续部署的第一护具; 再配特性开关、监控与可前后兼容的迁移。流水线快与检查全都很重要,但它们属于 CI 那一层。

3. 流水线全绿,但线上还是旧版本,说明什么?

对。绿只证明检查过了;线上没变说明没有部署这一步,或部署前留了人工确认 —— 这正是持续交付的常态,不是故障。
