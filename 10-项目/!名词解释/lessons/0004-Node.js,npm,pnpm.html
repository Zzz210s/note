Node.js 与三个包管理器:一层跑代码,一层取包

这节课的胜利:把跑代码的那一层和取包的那一层分开,并说出包到底存在哪三个地方。 读完你遇到"装不上 / 找不到模块"就能先判断该查版本、查锁文件还是查路径,而不是背命令。

一句话定位

它们常被并排提起,却不在同一层:Node.js 是运行时(让 JavaScript 在浏览器外执行), npm / pnpm / yarn 是包管理器(把别人的代码取回来、装进项目、写进锁文件记账)。 一个直接证据:本机 node -v 是 v24.14.0、npm -v 是 11.9.0 —— 两个版本号各自独立。

为解什么痛点而生

Node.js:让 JS 长脚上岸

痛点:JavaScript 起初只能活在浏览器里 —— 想写后端、写命令行工具、写构建脚本,就得换语言。 定义:Node.js 是让 JavaScript 能在浏览器之外运行的运行时环境,基于 V8 引擎构建 (Node.js 官方:Introduction to Node.js)。 大白话:给这门语言装了台通用发动机 —— 原来只能在泳池里游的鱼,现在能上岸跑。

npm(外加 npx 与 corepack):取包 + 借用 + 换挡

痛点:早期复用别人的代码靠"手动拷文件 + 口头约定版本",依赖失控、"在我机器上是好的"成了常态。 定义:npm 是随 Node.js 一同分发的包管理器,负责从 registry 取包、安装、升级, 并把结果记进 package.json 与锁文件 (npm 官方:About npm、 npm 官方:package-lock.json)。 大白话:npm 是应用商店加快递员;npx 是"试一下就走"的窗口 (npm 官方:npx); corepack 是包管理器自己的换挡杆,按项目声明的版本切换 npm / pnpm / yarn (Node.js 官方:corepack)。

pnpm(与 yarn):同一个包,全机只留一份

痛点:npm 的老毛病 —— 每个项目把依赖真身拷一份(20 个项目 20 份,吃磁盘)、复制几十万小文件很慢、 依赖被拍平后你能 import 一个没有声明过的包(幽灵依赖)。 定义:pnpm 用内容寻址的全机包仓库 + 硬链接装依赖,项目里的 node_modules/ 放的是指向仓库的链接, 依赖树严格按声明来(pnpm 官方:Motivation、 pnpm 官方:符号链接布局、 pnpm 官方:pnpm store)。 yarn 与 npm 同层,凭目录里的 yarn.lock 认得出来 (Yarn 官方:yarn.lock)。 大白话:全机只留一份真身,项目里放"链接"而不是"拷贝",顺手把偷用别人依赖的路堵死。

课里才有:包其实存在三个地方,路径各不相同

"包装到哪儿去了"是这段最容易含糊的地方。下面命令与输出原样照抄(在用户目录下跑):

$ npm root                    # 项目本地的依赖目录
C:\Users\23652\node_modules
$ npm root -g                 # npm 的全局安装目录
C:\Users\23652\AppData\Roaming\npm\node_modules
$ pnpm list -g --depth=0      # pnpm 的全局安装目录(和上面不是一个)
C:\Users\23652\AppData\Local\pnpm\global\v11 (PRIVATE)
└── @earendil-works/pi-coding-agent@0.87.1
$ pnpm store path             # 全机共享的包仓库
F:\.pnpm-store\v11
  • 两个包管理器的"全局"不是同一个目录:npm 的在 AppData\Roaming\npm(本机 9 个包), pnpm 的在 AppData\Local\pnpm\global\v11(只有 1 个)。"我装过了"得先说清是谁装的。
  • 全局是给命令行用的,不是给 import 用的:本机 node -e "require.resolve('npm')" 返回 MODULE_NOT_FOUND,尽管 npm 就装在这台机器上 —— 模块解析只沿"当前目录往上找 node_modules" (Node.js 官方:Modules),全局目录不在那条路上。
  • 硬链接要求同一分区:本机仓库在 F:,项目若在 C: 盘,省磁盘的好处会退化成复制。

课里才有:两边的 registry 是同一份配置

$ npm config get registry
https://registry.npmjs.org/
$ pnpm config get registry    # 与 npm 同一个值 —— 读的正是上面那份配置
https://registry.npmjs.org/
$ npm config get userconfig
C:\Users\23652\.npmrc

所以换镜像源通常改一处就够。

辨析练习:这句话在说哪一层?

共 4 例。判定靠"它在跑代码、在取包、在借用一次,还是在存放包"。

1. 敲下 node server.js,一个 HTTP 服务开始监听端口。

是运行时:它在执行代码。npm / pnpm 在这一步完全没有出场。

2. 敲 pnpm add lodash,包进了 node_modules,锁文件也多了一行。

是管理器:取包 + 记账(写进锁文件)正是它的两个核心动作。

3. 敲 npx cowsay hi,跑完一次,机器上没多留下什么。

是执行器:定位就是"取一次、跑一次、不长期留";项目真正依赖的必须写进 package.json。

4. pnpm store path 打印出 F:\.pnpm-store\v11。

是包仓库:它既不取包也不执行,只负责全机保存依赖真身,项目里用链接指过来。

自测(选项一样长,别从长度上猜)

1. 四个说法里,哪一个描述的是运行时?

对。运行时负责执行代码:B 是包管理器,C 是 pnpm 的包仓库,D 是 npx —— 四个都在场,只有一个在这层。

2. 一个包用全局方式装过了,这意味着什么?

对。实测 require.resolve('npm') 返回 MODULE_NOT_FOUND。 A 说得太绝(目录下恰好有 node_modules 时也能解析到),C、D 是想象出来的行为。

3. node_modules/ 与锁文件,哪个该进版本库?

对。锁文件记录"装哪些确切版本与来源",是可复现的依据;node_modules/ 是可重建的产物。 B 忽略了"没有锁文件就可能装出不同版本"。
