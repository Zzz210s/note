测试夹具:把前提固定住,再开工

这节课的胜利:看到"夹具(fixture)"时能立刻判断它指的是 提前摆好的条件、一批固定的输入,还是一个自包含的测试脚本; 并说清它和 mock / stub / 测试数据的边界。

一句话定位

夹具是 fixture 的翻译,借自机械加工:把工件夹在确定位置,刀具走的路径才有意义 (Wikipedia: Test fixture)。 软件测试借的是同一个隐喻 —— 把"被测对象的前置条件"固定住,让每次运行具有可比性, 所以它天然带两个动作:准备(setUp) 与 收尾(tearDown) (Python 官方:unittest)。

为解什么痛点而生

含义一:固定前提的机制

痛点:同一个功能这次测能过、下次又不行 —— 因为开始时机器状态不一样(残留的旧数据、临时文件、不同的环境变量)。 原因没变结果却变了,测试就失去可信度。 定义:夹具是在测试执行前把系统置入确定状态、结束后恢复原状的机制,通常成对出现 (pytest 官方:How to use fixtures)。 大白话:上台前先把布景、灯光、道具摆成固定位置;每次开演前都一样, 观众(测试)看到的差异就只能来自演员(被测代码)。

含义二:一批预先备好的输入

痛点:要验证"检查工具能识别坏写法",得先有坏写法的样本;每次手工造既费时又不一致,还说不清覆盖了哪些分支。 定义:夹具是一组预先准备好的输入(小仓库、样例文档、坏配置),被测试程序读入以触发特定分支 (Wikipedia: Test fixture 的 "fixed state" 说的就是这类被固定下来的东西)。 大白话:老师提前备好的"标准题卡" —— 每道题都想好了要考哪个知识点。

含义三(本项目报告里最常指的那个):一个自包含的测试脚本

痛点:交付物是一堆脚本与手册,靠人工点一遍验证 —— 不可重复、漏得多,也说不清"到底验过什么"。 定义:夹具是一个自包含的 runner:准备好输入、调用被测程序、逐条列断言,最后打印 PASS=n FAIL=m。 大白话:把验收清单写成代码 —— 机器照着清单逐条问"对不对",最后报"过了几条、错了几条"。

对比表:谁也不许混进别人那一格

名字一句话判定它提供什么失效场景
夹具(fixture)它把开演前的舞台摆成固定位置确定的环境 / 状态 / 样例输入(含准备与收尾)夹具自己写错就误报;被放宽就等于把风险藏起来
mock它自带期望,不合就自己判失败预置的交互契约(次数 / 参数 / 顺序)期望钉死交互细节,实现一改就红
stub它会念写死的台词固定的返回值 / 固定状态它在替你的代码回答 —— 死值错了测试照样绿
fake它有真本事但走捷径能用的替代实现(内存数据库)它自己也有 bug,与真实现的差异会悄悄积累
spy它包在真货外面记账,本体照跑调用记录,真实行为不变只观察不隔离,依赖还是真的
测试数据它是喂进去的原料,不是机制一批数据本身(边界值、坏样例)数据自己不合法,或覆盖不到目标分支

替身家族(除夹具与数据外)的分界出自 Martin Fowler 的 Test Double,完整清单见 Wikipedia: Test double。 关系不是并列而是嵌套:mock / stub / fake 常作为夹具准备出来的一部分被注入被测代码; 夹具管"整台机器的初始状态",替身管"某一个外部依赖装得像不像"。

它的真身只做两件事:把前提指到一个临时目录,然后断言(节选):

with tempfile.TemporaryDirectory() as d:      # 前提:临时目录,跑完自动删
    root = Path(d)
    L.VAULT_ROOT = root                       # 把"库根"指过去 —— 后面全在假库里跑
    _mk(root, "20-领域/a.md", "...[断](<../nowhere.md>)")
    assert len(C.check_links()) == 1, C.check_links()   # 断言:恰好 1 处断链

把断言拿掉会怎样?只剩"我觉得应该报了"。断言不成立时它当场报出期望多少、实际多少,并以非零退出码收场:

$ python -c "assert len([]) == 1, '应为 1 处,实际 0 处'"

  File "<string>", line 1, in <module>
    assert len([]) == 1, '应为 1 处,实际 0 处'
           ^^^^^^^^^^^^
AssertionError: 应为 1 处,实际 0 处        # 退出码 1

本机 16 个自检夹具合计 131 个用例(内里 233 条 assert 语句),全 PASS / FAIL=0。这就是"反馈环"的样子: 跑一条命令,立刻知道过了几条、哪条没过。

辨析练习:四样东西,哪一格?

共 4 例。判定靠"它在摆前提、在当替身、在当原料,还是在给判据"。

1. 准备一批边界值(空文件、超长行、缺字段的文档),直接喂给被测函数当输入。

是原料类:一批数据本身,既不是环境准备也不是替身 —— 喂它的那套装置才叫夹具。

2. 逐条声明"此处应当恰好报 1 处",不成立就打印期望值与实际值并让进程退出码非零。

是判据类:断言 —— 只有它给出"对 / 不对",前三种都只提供条件。

3. 开测前把库根指向一个临时目录,结束后自动删掉,好让每次跑的环境都一样。

是前提类:这是夹具最经典的含义一 —— 准备 + 收尾,把环境固定住。

4. 用一个"读文件必定返回 OK"的假对象,替掉被测代码里那个真去连网络的对象。

是替身类:stub 的典型形态 —— 写死的返回值,替某个外部依赖上场。

自测(选项一样长,别从长度上猜)

1. 夹具(fixture)与 mock 最根本的区别是什么?

对。夹具把"开始测试前的状态"固定住(含准备与收尾),替身替掉某个外部依赖 —— mock 常常只是夹具准备出来的一件东西。四者不是并列,而是嵌套。

2. 夹具报红时,第一步该做什么?

对。夹具本身也是被审查对象:夹具写错就改夹具,被测代码错就改代码。 A 与 B 都是把问题藏起来 —— 一个会误报的检查器,很快就会被所有人忽略。

3. 夹具全部通过,能证明什么?

对。夹具证明的是逻辑与契约,证明不了硬件、内容正确性、是否够格发布。 本项目的做法是:没在真机验过的必须在文档里显式声明 —— 不许用夹具全绿去暗示。
