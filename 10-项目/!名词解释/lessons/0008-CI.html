CI(持续集成):把你手动跑的那条命令,改成推送就自动跑

这节课的胜利:说清 CI 到底自动化了哪件事,亲眼读一次真实运行记录,并知道「本地过了」与「CI 过了」差在哪。 读完你再看「等 CI 绿了再合并」这句话,就知道那台云端机器此刻在替谁按开关。

一句话定位

CI 不是一个软件,是一条规矩:每个人至少每天把自己的改动合进同一条主线,并且每一次这样的合并都由自动化构建(含测试)验证 (Martin Fowler: Continuous Integration)。 维基百科的措辞是「频繁集成源码改动,保证集成后的代码库处于可用状态,通常由自动化系统来构建与测试」 (Wikipedia: Continuous integration)。 大白话:把「攒两周一起合」换成「天天合、合完自动验」 —— 谁把主线弄坏了,当场就知道。

为解什么痛点而生

攒着的分支,合起来会炸

痛点:多人各改各的,谁也不知道别人的改动会不会把自己搞崩;直到要发布那天才把几周的分支合到一起,冲突与 bug 一起爆发。这有个名字,叫集成地狱。 定义:CI 要求频繁集成(Fowler 引 Kent Beck 的原话「代码不要超过几个小时还没被集成」),并用自动化构建验证每次集成,以便尽早发现集成错误。 大白话:与其等着一起体检,不如每天量一次血压 —— 出问题的窗口从「两周」压到「一次提交」。

光有工具不算 CI

痛点:很多项目装了流水线,却只在功能分支上跑,主线照样一天才合一次 —— 这被误叫成「我们有 CI」。 定义:Fowler 专门划了这条界:只在功能分支上跑自动构建只是半集成;真正的 CI 要求「每个人都往主线推,每次推都触发构建」。 大白话:把「CI 服务」当成 CI 本身,就像把跑步机当成跑步 —— 器材不等于习惯。

课里才有①:读一次真实的运行记录

本机另一个仓库 Zzz210s/ai-session-hub 真接了 CI。下面是 2026-09-25 现跑 gh run list 的原始输出(时间倒序): 

$ gh run list -R Zzz210s/ai-session-hub --limit 5
completed  success  test: 删除相关用例改为平台无关(修 CI 在 Linux 上失败)  test  master  push 35519548484  10s
completed  failure  chore: package.json 关键词补全(CRLF 导致上次未生效)        test  master  push 35519431229  11s
completed  failure  fix: 补入被误忽略的 src/live/(克隆后无法运行)+ 关键词      test  master  push 35519243094   8s
completed  failure  chore: 加入 CI、版本 0.5.0、描述与关键词更新               test  master  push 35519029229  10s

这四行就是 CI 的全部意义:连续三次红,改到第四次绿。每次 git push 之后 8~11 秒,一台云端机器重跑了同一套检查并留下记录 —— 人不在场,也不用记得跑。那个仓库的 workflow 一共三件事,每件都是「人本来要手动做的事」:

阶段命令手动版本就是
单元测试node --test test/*.test.js自己在本地敲一遍
shell 语法检查bash -n setup.sh自己记得检查一遍脚本语法
误提交检查grep -rnE "C:\\Users\\..." .人肉翻自己有没有把家目录路径提交上去

它的注释里写着一条诚实的边界:Windows 专属能力(UIA 标签聚焦、系统回收站、ConPTY)在 CI 里覆盖不到,只能靠本机验证。 所以 CI 覆盖的是「换台 Linux 机器也能跑的那一半」—— 不是全部。

课里才有②:CI 就是把手动命令原样搬上去

本笔记库自己的检查是手跑的,输出与退出码如下(2026-09-25,--quiet 只打分类计数):

$ cd F:/0-Note/50-资源/工具/vault-check && PYTHONIOENCODING=utf-8 python -B check_vault.py --quiet; echo rc=$?
[A1 断链] 0 处
[A4 项目索引覆盖] 0 处
......                          # 共 13 行分类计数,一律 "0 处"
[A14 索引页一致性] 0 处
结论:PASS
rc=0

把这条命令写进配置,CI 就在了。给本库接 GitHub Actions 的最小骨架(逐行讲): 

name: vault-check                    # 剧本的名字,会出现在运行列表里
on:
  push: { branches: [master] }       # 推送到 master 时触发
  pull_request:                      # 提 PR 时也触发
  workflow_dispatch:                 # 允许在网页上手动点一次
jobs:
  check:
    runs-on: ubuntu-latest           # 用一台临时 Linux 机器,跑完就销毁
    steps:
      - uses: actions/checkout@v4    # 第 1 步:把仓库拉下来
      - name: 结构体检                # 第 2 步:跑那条本来就该手动跑的命令
        run: cd 50-资源/工具/vault-check && python -B check_vault.py --quiet

三层结构记成一句话:workflow = 剧本,job = 一幕,step = 一句台词;三层各一行就能跑 (GitHub 官方: Workflow syntax)。 一个真实约束:本库目前没有 .github/workflows/(2026-09-25 实测),所以上面只是骨架 —— 要不要接上,是另一个决定。

对比表:谁跟谁不是一回事

名字它做什么什么时候跑和 CI 的关系
测试夹具(fixture)摆前提 + 逐条断言,报 PASS=n FAIL=m被调用时CI 里跑的内容之一(0005)
linter检查单篇文本格式写的时候 / 提交前同一类检查,通常也塞进 CI
巡检器(vault-check)跨篇结构检查,结论落在退出码手动 check_vault.py上面那条命令的手动版(0006)
CI 服务(Actions)在云端按配置自动跑上面那些推送 / 提 PR / 定时CI 实践的载体,不是 CI 本身
CD(交付/部署)把验证过的产物送到待发布或已发布检查通过之后CI 的下一步,常写在同一个 workflow 里

一句话:夹具、linter、巡检器都是「检查」,CI 是「让检查自动发生」的那套规矩与场地。

辨析练习:这件事归谁管?

共 4 例。判定靠「它是内容、是单篇格式、是跨篇结构,还是让它们自动发生」。

1. 改完一批笔记,自己开一个终端敲一条命令,看有没有断链、有没有孤篇。

是结构巡检:看的是页与页之间的关系,而且是人手动敲的那一次。

2. 规定一级标题只能出现一次、标题层级不许跳级、列表前后要留空行。

是文本检查:盯的是一页之内的排版,不涉及页与页的关系 —— 这类活归 linter。

3. 每次推送之后,一台云端机器自动把上面两件事重做一遍,并把结论留在网页上。

是持续集成:内容没变,变的是「谁在什么时候跑」—— 从人的记忆换成了推送事件。

4. 写下一个断言「此处应当恰好报 1 处」,不成立就打印期望与实际,并让退出码非零。

是测试夹具:只有它逐条给出「对 / 不对」。CI 与巡检器都用它,但它自己不是自动触发器。

自测(选项一样长,别从长度上猜)

1. 严格按 Fowler 与维基的说法,CI 这个词指的是什么?

对。CI 是实践:频繁合进主线 + 每次合并都自动验证。另外三个说的是它的零件:构建命令、构建机器、云端工具 —— 有零件不等于有这条规矩。

2. 一次 CI 跑成绿色,能证明什么?

对。绿只覆盖「配置里写了的那几项」。本机那个仓库的注释就写明 Windows 专属能力覆盖不到; 发布还要人判断范围、兼容与回滚 —— 这和巡检器那条「没报不等于查过」是同一条纪律。

3. 只在功能分支上跑自动构建,按 Fowler 的说法算什么?

对。分支上的自动构建有用,但只是半集成;CI 的关键那条是「每个人都往主线推,每次推都触发构建」。 「必须每天发布才算持续集成」把 CI 和 CD 混了 —— 每天发布是持续交付/部署,不是 CI 的门槛。
