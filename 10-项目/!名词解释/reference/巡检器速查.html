巡检器 / 一致性检查器速查

它只做一件事:把「这批文件还讲不讲道理」翻译成一组可机器判定的规则,跑一遍重算全部, 逐条报 规则 · 文件:行号 · 原因,并把结论放进退出码。读它只读三样:哪一条、在哪儿、过没过。

输出三件套(这类工具的通例)

看什么长什么样(示例)用途
哪一条[R3 断链] 2 处分类计数:哪类规则命中了、各几处
在哪儿缩进的 docs/a.md:12 ../nowhere.md文件 + 行号 + 原因,直接跳过去改
过没过结论行 + 退出码给人看红绿,给流水线当判断依据

退出码的用法:0 = 全部通过,非 0 = 至少一条真问题 (Wikipedia: Exit status); 所以 checker --quiet || echo "还有问题" 这种写法能直接接进脚本与 CI。

判定表:看到什么,归哪一类

你注意到的现象哪一类规则会报修法
点开链接发现目标不存在链接与引用改路径,或补建目标文件
一篇文档从没有被别处引用过结构与数量(孤立文档)在目录页 / 索引里登记一行链接
目录页的统计数字与实物对不上结构与数量按实物改写统计行
字段缺失,或值不在约定集合里元数据校验按约定补齐字段或改值
标题层级跳级、行尾空格、行宽超限格式与排版(linter)按规则修排版
同一个标签一处大写一处小写命名一致性统一成约定写法
文件不在它该在的目录下归属检查搬进约定目录
没改内容,只把一条规则调严,老文件全红了规则本身(不是文件)先在假仓库里跑一遍自测,再决定是否收紧

这一类里常见的工具与分工

它查什么常见做法
链接与引用(断链、双链失效)文档站构建时的死链检查、专门的 link checker(Wikipedia: Link rot)
格式与排版各类 linter(markdownlint / ESLint / 语言内置的 --check 之类),规则集通常可配置(Wikipedia: Lint)
结构与数量(索引、统计、归属)项目自写的脚本 —— 规则是项目自己的,没有通用产品
某个程序的行为是否等于预期测试框架(pytest / node --test / JUnit 等),那是测试,不是巡检
什么时候跑提交前用 pre-commit;推送后用 GitHub Actions 这类 CI (Wikipedia: Continuous integration)

边界:0 处不等于「查过了」

一条规则报 0 处,有三种可能,别急着当证据:

  • 真的干净:全库确实没有命中。
  • 被豁免:规则只对某类文件 / 某个目录生效,你关心的那部分根本不在管辖范围里。
  • 短路跳过:前置条件不满足时它直接返回(例如「连目标目录都不存在,就跳过这一条」), 连算都没算。

要确认,就把那条判据单独拎出来跑一次 —— 拿一个已知该报的样本喂给它,看它报不报。 检查器自己也要被检查:好的实现会带一组自测,在临时目录里造一个假仓库,验证「该报的报了、不该报的没报」 (Wikipedia: Test fixture)。

易混点

  • 它是静态检查,不运行内容:查结构与文本,查不到事实错误、语义对不对。
  • 它与 linter 谁也不替代谁:一个管文件之间的关系,一个管单文件内的排版。
  • 全绿只说明「规则内自洽」:规则没写到的东西,绿也证明不了。
  • 规则越多越安全是错觉:误报多了,人会集体无视红灯 —— 信噪比比条数重要。
  • 它不会自己变聪明:新出现的坏形状要有人先把它写成一条规则,机器才看得见。
