CI/CD(持续集成 / 持续交付 / 持续部署)速查

按顺序问三个问题:它有没有自动跑 → 自动到哪一步为止 → 最后那一下谁按。 三个都有答案,「这个项目走到哪一层」就有答案了。

三层速览与三个数字

层一句话人还要做什么
CI(持续集成)每个成员至少每天一次把改动合进主线,每次合并都由自动化构建(含测试)验证决定合不合
持续交付(delivery)CI 通过后自动打包成「随时可发布」,上不上线由人决定按一下发布按钮
持续部署(deployment)验证通过就自动进入生产,没有人工确认出问题才介入
数字 / 事实值出处
集成频率代码不要超过几个小时还没被集成(Kent Beck)Fowler: Continuous Integration
构建时长XP 经验值:十分钟内(每砍一分钟,每人每次提交都省一分钟)同上
两个 CD 的分界只差一步:生产上线前那一次人工确认Fowler: Continuous Delivery
术语出处CI 一词 1991 年由 Grady Booch 提出Wikipedia: Continuous integration

判定表:看到这个,就是这个结论

你观察到的现象结论判据
仓库里根本没有流水线配置文件没接 CI没有触发入口,推送不会自动跑任何东西
有配置文件,但只在功能分支上跑半集成,不是 CIFowler:关键那条是「每个人都往主线推,每次推都触发构建」
每次推送后几十秒出现一条运行记录CI 在工作「推送」这个事件命中了
只跑构建与测试,没有任何发布动作只有 CI流水线到「检查」就结束了
产物已就绪,上线要人点一下持续交付那一下点击就是 delivery 与 deployment 的分界
通过后几分钟线上自动换版,没人点过持续部署没有人工确认这一环
自动上线,但只到预发环境持续交付(到 staging)生产那一跳还留着人
最近几条都是失败主线可能已坏,先修红线「主线坏了立刻修」是 CI 的第一条纪律
本地全过、云端红两边环境不同,或用例写死了平台系统、路径大小写、换行符(CRLF)都会造成这种差
必须有绿才能合并分支保护把 CI 结论变成了制度CI 的价值一半在自动跑,一半在「红了不让合」
绿了但线上还是旧版本只走到交付,没走到自动部署检查过了 ≠ 部署过

持续部署的前提清单(缺一条,自动上线就只是自动出事)

前提为什么必须有
CI 本身可靠检查拦不住问题,自动上线就是把问题自动送进生产
可一键回滚自动发得出去,也要能自动收回来;否则一次坏版本就是一次事故
特性开关(feature flag)代码先上线、功能后开,把「部署」与「发布」拆成两件事
监控与告警自动上线的前提是能自动发现「上线之后坏了」
数据库迁移可前后兼容新旧两个版本会同时存在几分钟,迁移不能只朝一个方向走

相关名词:Feature toggle · Blue-green deployment。

workflow 三层结构

层是什么关键字段
workflow一个配置文件 = 一份剧本名字 / 触发事件 / 作业列表
job一幕:在某一台机器上跑的一串步骤跑在哪种机器 / 步骤列表 / 环境(可挂人工批准)
step一句台词:一条命令,或一个可复用的动作命令 / 引用某个动作 / 名字

最小骨架(通用形状,逐行注)

name: check-and-deploy
on:
  push: { branches: [main] }        # 推送主分支时触发
  pull_request:                     # 提 PR 时也触发
jobs:
  check:                            # 这一幕 = CI:跑检查
    runs-on: ubuntu-latest           # 临时 Linux 机器,跑完即销毁
    steps:
      - uses: actions/checkout@v4    # 第 1 步:把仓库拉下来
      - run: npm ci && npm test     # 第 2 步:装依赖 + 跑测试(退出码非 0 即红)
  deploy:                           # 这一幕 = CD
    needs: check                    # 检查绿了才轮到部署
    environment: production         # 挂「必须人工批准」→ 持续交付
    steps:
      - run: ./deploy.sh            # 不挂批准 → 持续部署

一个字段决定层次:environment 上挂「必须人工批准」,这套就是持续交付; 去掉批准,同一套就是持续部署 (GitHub: Workflow syntax · Quickstart)。 再往后才轮到缓存、矩阵(多系统 × 多版本)、金丝雀放量。

症状反查

症状先看典型原因
推送后一直没有运行记录触发事件与分支过滤推的是别的分支,或只配了「提 PR 时触发」
本地过、流水线红失败那一步的完整日志平台差异、路径大小写、换行符(CRLF)、用例写死平台
流水线很慢各步骤耗时每个作业都重装依赖、没用缓存
检查通过了但问题还在流水线里到底跑了几件事覆盖不到那些事 —— 绿只说明「配置里那几项过了」
绿了但线上还是旧版本有没有部署这一幕只做到交付;或部署前留了人工确认
自动上线后出了事故回滚与特性开关前提清单没补齐 —— 自动发得出去却收不回来
改了流水线配置却没生效文件是否在默认分支、YAML 是否合法配置文件本身要先合进默认分支才会被采纳

易混点

  • CI ≠ 跑测试:构建、静态检查、密钥扫描、依赖审计都算。它管「这次集成有没有坏」。
  • CI ≠ 某个 CI 服务:托管平台只是场地;CI 是「每天往主线合 + 每次合都验证」这条规矩。
  • 功能分支上的自动构建 = 半集成:有用,但不是 CI。
  • CD 有两个 D:delivery(人按一下)与 deployment(机器按);听人只说「CD」时先问是哪个。
  • 持续部署不是「更高级的口号」:它是把人工确认那一步去掉,前提是回滚、监控、特性开关都到位。
  • 绿不是「可以发布」:它只覆盖配置里写了的那几项。
