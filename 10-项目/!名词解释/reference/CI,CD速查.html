CI/CD(持续集成 / 持续交付 / 持续部署)速查

按顺序问三个问题:它有没有自动跑 → 自动到哪一步为止 → 最后那一下谁按。 三个都有答案,「这项目走到哪一层」就有答案了。

三层速览与三个数字

层一句话人还要做什么
CI(持续集成)每个成员至少每天一次把改动合进主线,每次合并都由自动化构建(含测试)验证决定合不合
持续交付(delivery)CI 通过后自动打包成「随时可发布」,上不上线由人决定按一下发布按钮
持续部署(deployment)验证通过就自动进入生产,没有人工确认出问题才介入
数字 / 事实值出处
集成频率代码不要超过几个小时还没被集成(Kent Beck)Fowler: Continuous Integration
构建时长XP 经验值:十分钟内(每砍一分钟,每人每次提交都省一分钟)同上
两个 CD 的分界只差一步:生产上线前那一次人工确认Fowler: Continuous Delivery
术语出处CI 一词 1991 年由 Grady Booch 提出Wikipedia: Continuous integration

判定表:看到这个,就是这个结论

你观察到的现象结论判据
仓库里没有 .github/workflows/没接 CI(本库就是这种)没有触发入口,推送不会自动跑任何东西
有 workflow,但只在功能分支上跑半集成,不是 CIFowler:关键那条是「每个人都往主线推,每次推都触发构建」
每次 push 后几十秒内出现一条运行记录CI 在工作触发器 on: push 命中了
只跑构建与测试,没有任何发布动作只有 CI流水线到「检查」就结束了
产物已就绪,上线要人点一下持续交付那一下点击就是 delivery 与 deployment 的分界(本机 GoodNight:打 tag 那一下)
通过后几分钟线上自动换版,没人点过持续部署没有人工确认这一环(本机 personal-content:push 就 curl deploy hook)
自动上线,但只到预发环境持续交付(到 staging)生产那一跳还留着人
最近几条都是 failure主线可能已坏,先修红线「Fix Broken Builds Immediately」
本地全过、云端红两边环境不同或用例写死了平台本机实测那次:CI 在 Linux 上失败,本机看不见
必须有绿才能合并分支保护把 CI 结论变成了制度CI 的价值一半在自动跑,一半在「红了不让合」

持续部署的前提清单(缺一条,自动上线就只是自动出事)

前提为什么必须有
CI 本身可靠检查拦不住问题,自动上线就是把问题自动送进生产
可一键回滚自动发得出去,也要能自动收回来;否则一次坏版本就是一次事故
特性开关(feature flag)代码先上线、功能后开,把「部署」与「发布」拆成两件事
监控与告警自动上线的前提是能自动发现「上线之后坏了」
数据库迁移可前后兼容新旧两个版本会同时存在几分钟,迁移不能只朝一个方向走

workflow 三层结构

层是什么关键字段
workflow一个 .github/workflows/*.yml 文件 = 一份剧本name / on / jobs
job一幕:在某一台机器上跑的一串步骤runs-on / steps / environment
step一句台词:一条命令,或一个可复用的 actionuses / run / name

最小骨架(逐行注;本库尚未接入,2026-09-25 实测无 .github/)

name: vault-check                    # 剧本名,出现在运行列表里
on:
  push: { branches: [master] }       # 推送 master 时触发
  pull_request:                      # 提 PR 时也触发
  workflow_dispatch:                 # 允许在网页上手动点一次
jobs:
  check:                             # 这一幕 = CI:跑检查
    runs-on: ubuntu-latest           # 临时 Linux 机器,跑完即销毁
    steps:
      - uses: actions/checkout@v4    # 第 1 步:把仓库拉下来
      - name: 结构体检                # 第 2 步:跑那条本来该手动跑的命令
        run: cd 50-资源/工具/vault-check && python -B check_vault.py --quiet
  # deploy:                          # 再加这一幕 = CD(下面两种二选一)
  #   needs: check                   # 检查绿了才轮到部署
  #   environment: production        # 给它配「必须人工批准」→ 持续交付
  #   steps: [ ...vercel deploy / wrangler deploy... ]   # 不配批准 → 持续部署

一个字段决定层次:environment 上挂「必须人工批准」,这套就是持续交付;去掉批准,同一套就是持续部署 (GitHub: Workflow syntax)。 再往后才轮到缓存、矩阵(多系统 × 多版本)、金丝雀放量。完整演进见 CI/CD 与 GitHub Actions 实战。

CD 的出口不必是部署 CLI —— 一个 deploy hook(只含令牌的 URL,POST 一下就触发平台构建)就是:

# personal-content/.github/workflows/trigger-site.yml(全文 14 行,逐字)
name: trigger-site

on:
  push:
    branches: [main]

jobs:
  trigger:
    runs-on: ubuntu-latest
    steps:
      - name: Call Cloudflare Pages deploy hook
        run: curl --fail --silent --show-error -X POST "$CF_DEPLOY_HOOK_URL"
        env:
          CF_DEPLOY_HOOK_URL: ${{ secrets.CF_DEPLOY_HOOK_URL }}
# GoodNight/.github/workflows/ci.yml(68 行,下为节选;行内 ← 注为本文所加)
on:
  pull_request:
  push:
    branches: [main]
    tags: ['v*']
permissions:
  contents: write                    # ← 注:建 Release 需写权限
jobs:
  test:
    runs-on: ubuntu-latest
    if: ${{ !startsWith(github.ref, 'refs/tags/') }}
    steps:
      - run: ./gradlew test
  release:
    runs-on: ubuntu-latest
    if: startsWith(github.ref, 'refs/tags/')
    steps:
      # (setup-java / setup-gradle / 签名 / APK 改名等步骤此处略)
      - run: ./gradlew assembleRelease
      - name: Publish to GitHub Release
        uses: softprops/action-gh-release@v2
        with:
          files: GoodNight-*.apk
          generate_release_notes: true
          draft: false

两个仓对照读,差别一句话:personal-content 连「人工按一下」都没有 = 持续部署;GoodNight 把「按一下」留成打 tag = 持续交付。运行记录也对得上:trigger-site 每次 push 后 7~8 秒绿,v2.2.0 的 tag 运行 3m41s 后 gh release list 里就出现 v2.2.0。

这两个是「持续部署」那一步的手动版:人敲 vercel deploy / wrangler deploy,产物才上线; 写进 workflow 的 deploy job,那一步就从「人敲」变成「检查通过后自动敲」。 学习出口:2027-掌握边缘函数原理 · 课程地图 第 5 节「动手:部署你的第一个边缘函数」。

本地那条命令(CI 里跑的就是它)

$ cd F:/0-Note/50-资源/工具/vault-check && PYTHONIOENCODING=utf-8 python -B check_vault.py --quiet; echo rc=$?
[A1 断链] 0 处
[A4 项目索引覆盖] 0 处
......                          # 13 行分类计数,一律 "0 处"
结论:PASS
rc=0

退出码 0 = PASS,非 0 = FAIL;CI 判红绿靠的正是这个退出码(Wikipedia: Exit status)。 所以「搬进 CI」不需要改代码,只要保证命令能在干净机器上跑起来(路径、编码、依赖都得自足)。

症状反查

症状先看典型原因
推送后一直没有运行记录on 的分支与事件推的是别的分支,或只配了 pull_request
本地过、CI 红失败那一步的完整日志平台差异、路径大小写、换行符(CRLF)、用例写死平台
CI 很慢各步骤耗时每个 job 都重装依赖、没用缓存
检查通过了但问题还在workflow 里到底跑了几件事覆盖不到那些事 —— 绿只说明「配置里那几项过了」
绿了但线上还是旧版本有没有 deploy job只做到交付;或部署前留了人工确认
自动上线后出了事故回滚与特性开关前提清单没补齐 —— 自动发得出去却收不回来
改了 workflow 却没生效文件是否在默认分支、YAML 是否合法workflow 文件本身要先合进默认分支才会被采纳

易混点

  • CI ≠ 跑测试:构建、静态检查、密钥扫描、依赖审计都算。它管「这次集成有没有坏」。
  • CI ≠ CI 服务:Actions / Jenkins 是场地;CI 是「每天往主线合 + 每次合都验证」这条规矩。
  • 功能分支上的自动构建 = 半集成:有用,但不是 CI。
  • CD 有两个 D:delivery(人按一下)与 deployment(机器按);听人只说「CD」时先问是哪个。
  • 持续部署 ≠ 持续交付的升级版口号:它是把人工确认那一步去掉,前提是回滚、监控、特性开关都到位。
  • 绿不是「可以发布」:它只覆盖配置里写了的那几项。
