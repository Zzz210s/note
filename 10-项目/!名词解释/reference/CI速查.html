CI(持续集成)速查

按顺序问三个问题:它有没有自动跑 → 跑在主线还是分支 → 跑成了什么颜色。 三个都有答案,「这项目到底有没有 CI」就有答案了。

一句话定义与三个数字

项值出处
CI 是什么每个成员至少每天一次把改动合进主线,每次合并都由自动化构建(含测试)验证Fowler: Continuous Integration
集成频率代码不要超过几个小时还没被集成(Kent Beck)同上
构建时长XP 经验值:十分钟内(每砍一分钟,每人每次提交都省一分钟)同上
术语出处CI 一词 1991 年由 Grady Booch 提出Wikipedia: Continuous integration

判定表:看到这个,就是这个结论

你观察到的现象结论判据
仓库里没有 .github/workflows/没接 CI(本库就是这种)没有触发入口,推送不会自动跑任何东西
有 workflow,但只在功能分支上跑半集成,不是 CIFowler:关键那条是「每个人都往主线推,每次推都触发构建」
每次 push 后几十秒内出现一条运行记录CI 在工作触发器 on: push 命中了
最近几条都是 failure主线可能已坏,先修红线「Fix Broken Builds Immediately」
本地全过、云端红两边环境不同或用例写死了平台本机实测那次:CI 在 Linux 上失败,本机看不见
运行记录里阶段数比预期少某步被 if 跳过,或配置里没写核对 workflow 的 on 与 jobs
灰 / queued没跑,别当成过和巡检器「没报不等于查过」同源
必须有绿才能合并分支保护把 CI 结论变成了制度CI 的价值一半在自动跑,一半在「红了不让合」

workflow 三层结构

层是什么关键字段
workflow一个 .github/workflows/*.yml 文件 = 一份剧本name / on / jobs
job一幕:在某一台机器上跑的一串步骤runs-on / steps
step一句台词:一条命令,或一个可复用的 actionuses / run / name

最小骨架(逐行注;本库尚未接入,2026-09-25 实测无 .github/)

name: vault-check                    # 剧本名,出现在运行列表里
on:
  push: { branches: [master] }       # 推送 master 时触发
  pull_request:                      # 提 PR 时也触发
  workflow_dispatch:                 # 允许在网页上手动点一次
jobs:
  check:
    runs-on: ubuntu-latest           # 临时 Linux 机器,跑完即销毁
    steps:
      - uses: actions/checkout@v4    # 第 1 步:把仓库拉下来
      - name: 结构体检                # 第 2 步:跑那条本来该手动跑的命令
        run: cd 50-资源/工具/vault-check && python -B check_vault.py --quiet

要加的第二件事通常是「先装依赖」(actions/setup-node 之类)与「结果落成产物」; 再往后才轮到缓存、矩阵(多系统 × 多版本)、只在 main 上跑的部署 job。完整演进见 CI/CD 与 GitHub Actions 实战。

本地那条命令(CI 里跑的就是它)

[A1 断链] 0 处

......                          # 13 行分类计数,一律 "0 处"
结论:PASS
rc=0

退出码 0 = PASS,非 0 = FAIL;CI 判红绿靠的正是这个退出码(Wikipedia: Exit status)。 所以「搬进 CI」不需要改代码,只要保证命令能在干净机器上跑起来(路径、编码、依赖都得自足)。

症状反查

症状先看典型原因
推送后一直没有运行记录on 的分支与事件推的是别的分支,或只配了 pull_request
本地过、CI 红失败那一步的完整日志平台差异、路径大小写、换行符(CRLF)、用例写死平台
CI 很慢各步骤耗时每个 job 都重装依赖、没用缓存
检查通过了但问题还在workflow 里到底跑了几件事覆盖不到那些事 —— 绿只说明「配置里那几项过了」
改了 workflow 却没生效文件是否在默认分支、YAML 是否合法workflow 文件本身要先合进默认分支才会被采纳

易混点

  • CI ≠ 跑测试:构建、静态检查、密钥扫描、依赖审计都算。它管「这次集成有没有坏」。
  • CI ≠ CI 服务:Actions / Jenkins 是场地;CI 是「每天往主线合 + 每次合都验证」这条规矩。
  • 功能分支上的自动构建 = 半集成:有用,但不是 CI。
  • CI ≠ CD:CI 保证不坏,CD(交付 / 部署)负责送出去。
  • 绿不是「可以发布」:它只覆盖配置里写了的那几项。
