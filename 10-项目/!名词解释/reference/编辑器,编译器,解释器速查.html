编辑器 / 编译器 / 解释器 / IDE 速查

只有一个问题需要回答:它在链路里干什么活。改文本是一层、把文本变成能跑的东西是另一层、把前两层打包成工作室是第三层。名字混起来,几乎都是把不同层当成了同一件事。

判定表:看到这个,就是那个

你观察到的现象结论判据
它让你写、让你改,但从不判断代码对不对编辑器只碰文本层
整份读完,产出一个新文件;改一行要重来一遍编译器翻译发生在运行之前
逐句读、当场执行,不留下可执行产物解释器翻译与执行交替进行
它一边解释着跑,一边把最热的代码编译成机器码JIT运行期优化,不是另一种语言分类
一个界面里集齐编辑、运行、调试、项目管理IDE集成外壳,把前几层包起来
装了它,代码还是跑不起来只装了编辑器层缺执行层
点了「运行」按钮却报找不到解释器 / 编译器集成外壳在替你调用执行层按钮本身不执行代码,它去喊执行层
报错信息里有 error: 和行号,整份没产出编译器在跟你说话解释器则是跑到那一句时才报错

编译器 / 解释器 / JIT:这一组怎么分

名字一句话判定什么时候它不适用
编译器翻译发生在运行之前,产物是文件改一处就得整份重来,交互式试验不顺手
解释器翻译和执行交替进行,产物只活在内存里解释开销让峰值性能长期落后于原生机器码
JIT解释着跑,顺手把热点编译成机器码冷启动与预热期更慢,内存占用也更高

混合形态:容易被当成「二选一」的三件事

实现先做什么再做什么留下的产物
CPython(Python 默认实现)把源码编译成字节码虚拟机逐条解释字节码.pyc 字节码缓存
JVM(Java / Kotlin 等)把源码编译成字节码解释执行,热点方法 JIT 成机器码.class 字节码文件
浏览器里的 JS 引擎解析成字节码 / 中间表示先解释,热点函数 JIT 成机器码一般不落盘,只在内存里

所以「解释型语言不做编译」是错的;判断一个工具是编译器还是解释器,看的是翻译产物给谁、什么时候执行,不是语言的名字。

典型命令(只用来辨认层级)

想知道的事命令形态
有没有解释器、是哪个版本python -V / node -v / ruby -v
有没有编译器、是哪个版本gcc --version / clang --version
把源代码编译成产物gcc hello.c -o hello
只做语法编译、不做成可执行文件python -m py_compile hello.py
看一段代码被编译成了什么python -c "import dis; dis.dis('x = 1 + 2')"

易混点

  • VS Code 出厂是编辑器;装了语言插件后能做补全、跳转、调试,和 IDE 的边界才变模糊 —— 那是"装上插件之后"。
  • 装了一整套重型 IDE 不等于装了执行层;反过来,只装解释器也能跑代码,只是写起来难受。
  • 调试器、Linter、语言服务器、构建工具是配套角色,不在这四层里;IDE 只是把其中几个收进同一个界面。
  • 「Python 是解释型语言」说的是默认实现 CPython 的执行方式,不排除别的实现先编译成机器码。
  • 同一个语言可以两头都有实现:官方解释器 + 把同一份源码编译成原生机器码的编译器,两者并行存在。
