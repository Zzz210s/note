# GRUB

> 按下电源键到屏幕上出现登录界面,中间有一小段几乎没人看的过程:固件找到磁盘上的一个程序,
> 那个程序把内核读进内存并把控制权交出去。GRUB 就是这一段的常客 —— 它也是多系统菜单背后那张脸,
> 以及"改了配置为什么必须重新生成"这句话的主角。
> **本文的固定写法**:每个概念按「**为解决什么痛点而生 / 一句话定义 / 大白话注解**」三段给出,再展开细节。
> 关联阅读:同批课程 [0012 · GRUB](../lessons/0012-GRUB.html)、速查卡 [GRUB 速查](../reference/GRUB速查.html);
> 相邻词条 [tmux](<tmux.md>) 讲的是开机之后、登录之后的事。

## 一句话速览

| 名称 | 一句话定义 | 大白话注解 |
| --- | --- | --- |
| **引导加载程序(bootloader)** | 固件交出的第一个"能认文件系统"的程序,职责是装载内核(必要时连 initramfs)并把控制权交出去 | 接力赛里接第一棒的人 |
| **GRUB** | 这一族里 Linux 世界最常见的实现,全称 GNU GRand Unified Bootloader | 多数发行版开机时默认的那个 |
| **固件(firmware)** | 主板(或虚拟机)上那段开机先跑的程序,负责自检并找到"可以引导的东西" | 起跑的发令枪 |
| **BIOS / UEFI** | 两代固件接口:旧的 BIOS,现在的 UEFI | 发令枪的两代产品 |
| **EFI 系统分区(ESP)** | 硬盘上一个 FAT 格式的小分区,专门放 `.efi` 可执行文件 | 固件配套的取件柜 |
| **启动项(boot entry)** | 固件自己保存的"去哪儿找哪个程序"的记录 | 取件单 |
| **initramfs** | 一份临时根文件系统,内核先靠它挂上真正的根分区 | 开机时的临时脚手架 |

**一句话判定**:问「**从按下电源到内核跑起来,这一步是谁在干**」——
认不了文件系统、只按固定位置加载的,是**固件**;能读分区上的文件、能弹菜单、能把内核交出去的,
是**引导加载程序**([Wikipedia: Bootloader](https://en.wikipedia.org/wiki/Bootloader) ·
[Arch Wiki: Arch boot process](https://wiki.archlinux.org/title/Arch_boot_process))。

## 一、它到底解决了什么

### 固件只认识很少的东西

> **为解决什么痛点而生**:刚通上电时,内存是空的、操作系统还不存在;能跑的只有主板上的固件。
> 固件要做的第一件事是自检,第二件事是"把控制权交给一个能继续往下走的东西"
> ([Wikipedia: Booting](https://en.wikipedia.org/wiki/Booting))。
> **一句话定义**:固件是一段写在主板(或虚拟机固件)上的程序,它对硬盘的认知很有限:
> 旧的 BIOS 基本只会读"第一个扇区",新的 UEFI 会去读一个 FAT 分区的特定路径
> ([Wikipedia: UEFI](https://en.wikipedia.org/wiki/UEFI))。
> **大白话注解**:固件像个只会开门的门卫 —— 它把门打开把人放进来,后面的事一概不管。

### 引导加载程序会「读文件」

> **为解决什么痛点而生**:内核通常是一个带版本号的文件(还配一份 initramfs),放在某个分区的目录里;
> 要让"门卫"记住每次升级后的路径不现实,也让多系统选择无法实现。
> **一句话定义**:引导加载程序是固件交出的第一个程序,它**自带读文件系统的能力**,
> 于是可以按名字去找内核、显示一份菜单让人选、把选中的内核与 initramfs 读进内存再跳过去
> ([Wikipedia: GNU GRUB](https://en.wikipedia.org/wiki/GNU_GRUB))。
> **大白话注解**:它不信"固定位置"这套,而是能自己翻目录、看菜单,认准了再把内核请上台。

### 三步接力:固件 → 引导加载程序 → 内核

| 阶段 | 谁在干 | 干的事 | 出问题时你会看到 |
| --- | --- | --- | --- |
| 1 · 自检 | 固件 | 点亮硬件、准备内存、找可引导的东西 | 屏幕一直黑、蜂鸣、进固件设置界面 |
| 2 · 引导 | 引导加载程序(GRUB) | 读配置、显示菜单、把内核与 initramfs 读进内存 | 卡在 `grub>` 提示符,或菜单里没有系统 |
| 3 · 交接 | 内核接手 | 解压自己、用 initramfs 挂上真正的根分区、最后启动 init / systemd | 花屏、内核行号报错、掉进紧急模式 |

三步的分界不在"谁更高级",而在**谁还认文件系统**:固件不认,GRUB 认,内核认全部。
第三阶段的一手说明见 [内核 x86 引导文档](https://docs.kernel.org/arch/x86/boot.html)。

## 二、对比表:五个容易混的名字

| 名字 | 一句话判定 | 什么时候它不适用 |
| --- | --- | --- |
| **GRUB** | 一个跑在磁盘上、会读文件系统的引导加载程序,常带多系统菜单 | 它管不了固件那一步;固件不认它,就轮不到它上场 |
| **UEFI 固件** | 主板上的程序:自检 + 按启动项去找 `.efi` 文件 | 它不读内核、不看多系统菜单;复杂逻辑不归它 |
| **传统 BIOS** | 上一代固件:只读第一个扇区、只认 16 位实模式 | 新机器普遍已转向 UEFI;老写法在新固件下常直接不回 |
| **Windows 启动管理器** | Windows 自己的引导程序,负责选系统并把它的内核交出去 | 它只认 Windows;双系统菜单通常是 GRUB 或固件在管 |
| **systemd-boot** | 另一种引导加载程序:只跑在 UEFI 上,条目就是普通配置文件 | 传统 BIOS 机器上它不适用;它的菜单比 GRUB 朴素得多 |

一句话分工:**固件管"我该把控制权交给谁",引导加载程序管"我要加载哪个内核",
内核管"我怎么把系统跑起来"**。多系统菜单只是引导加载程序的一个副产品
([Wikipedia: Multi-booting](https://en.wikipedia.org/wiki/Multi-booting) ·
[Arch Wiki: Systemd-boot](https://wiki.archlinux.org/title/Systemd-boot))。

## 三、菜单与配置:为什么「改完要重新生成」

| 你看到的东西 | 它在哪儿 | 谁写的 |
| --- | --- | --- |
| 真正被读取的配置 | 引导分区里的 `grub.cfg` | **由工具生成**,不该手改 |
| 你想改的默认项(默认系统、等待秒数) | `/etc/default/grub` | 你 |
| 每个菜单条目怎么拼出来 | `/etc/grub.d/` 里的脚本 | 你(或安装包) |
| 生成的命令 | `grub-mkconfig`(发行版常包一层 `update-grub`) | 你跑一次 |
| 装在哪儿、固件怎么找到它 | `grub-install` / 固件启动项 | 你跑一次 |

概念上只有一句话:**被读取的那份配置是"编译产物"** ——
你改的是原料(默认项与脚本),产物得重新生成才会变;直接手改产物,下一次生成就把它覆盖回去
([man grub-mkconfig](https://manpages.debian.org/testing/grub2-common/grub-mkconfig.8.en.html) ·
[Arch Wiki: GRUB](https://wiki.archlinux.org/title/GRUB))。
同理,"双系统菜单里没有另一个系统"多半不是引导坏了,而是生成时没把那个系统探测出来。

## 四、常见误解

| 说法 | 问题在哪 | 更准的说法 |
| --- | --- | --- |
| 「GRUB 就是 BIOS」 | 一个在主板固件里,一个在磁盘上 | 固件先跑,再把控制权交给 GRUB |
| 「开机菜单是操作系统画的」 | 那一刻还没有操作系统 | 菜单由引导加载程序(或固件)画出来 |
| 「装了系统就自动会出现在菜单里」 | 条目是生成配置时探测出来的 | 探测不到就不出现,得看探测机制 |
| 「改配置文件要手改那份被读取的」 | 它是生成物,下次生成就会被覆盖 | 改原料(默认项与脚本)再重新生成 |
| 「引导加载程序能救活一切」 | 它只负责到"把内核交出去"为止 | 内核起来之后的问题(驱动、挂载)不归它管 |

## 五、和相邻术语的关系

| 术语 | 一句话定义 | 与 GRUB 的关系 |
| --- | --- | --- |
| **MBR / GPT** | 硬盘开头的分区表两种格式 | 老固件按 MBR 的第一个扇区找 GRUB;UEFI 按 ESP 里的文件找它 |
| **引导分区 / `/boot`** | 存放内核、initramfs 与 GRUB 文件的地方 | GRUB 读的就是这里 |
| **initramfs** | 临时根文件系统 | GRUB 负责把它与内核一起读进内存 |
| **init / systemd** | 内核交棒后的第一个用户态进程 | 它在链条的下一环,与 GRUB 不直接打交道 |
| **Secure Boot** | UEFI 的一项签名校验机制 | 它会让未签名的引导加载程序不被执行,是"引导失败"的常见来源 |
| **固件启动菜单** | 固件自己那份"从哪儿启动"的选择 | 与 GRUB 的菜单是两回事:前者选程序,后者选内核 |

**一句话总结**:固件解决「**开机后先跑谁**」,引导加载程序解决「**加载哪个内核、怎么加载**」,
内核解决「**系统怎么跑起来**」;三段顺序固定,越往后越"认识"这台机器。
