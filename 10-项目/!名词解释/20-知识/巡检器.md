# 巡检器(vault-check)是什么

> 这个库里躺着一套自己写的"体检工具":`50-资源/工具/vault-check/`。一条命令跑完全库,告诉你哪条链接断了、哪篇笔记没人能到达、哪张索引页的统计数字对不上、哪篇成品知识没住进 `20-知识/`、哪篇知识笔记没写明来源项目、哪个项目还没建教学工作区。
> 本文讲它**为什么存在**、**怎么用**、**内部怎么运作**,以及它**查不到什么**。
> **本文的固定写法**:每个概念按「**为解决什么痛点而生 / 一句话定义 / 大白话注解**」三段给出。
> 关联阅读:[测试夹具是什么](<测试夹具是什么.md>)、[CLI、TUI、GUI 三种界面的区别](<CLI,TUI,GUI三种界面的区别.md>)。

---

## 一句话速览

| 名称 | 一句话定义 | 为解决什么痛点而生 |
| --- | --- | --- |
| **巡检器** | 一套本地 Python 脚本,把"这个笔记库还讲不讲道理"变成 14 条可自动判定的检查 | 库长到 141 篇后,断链、孤篇、元数据漂移靠人眼必然漏;漏了也没人告诉你 |
| **检查项(A1~A14)** | 14 条独立判据,每条只看一件事,报出`文件:行号 原因` | 一个"全库体检"如果只给一句"有问题",等于没查 —— 必须能定位到行 |
| **白名单 / 豁免** | 明确写下来的"这里断了是故意的"清单 | 模板占位、语法示例、刻意留的待补坑,会被任何朴素的检查器误报成错 |
| **自检(selftest)** | 用假库验证"该报的报了、不该报的没报" | 检查器自己写错了比不写更糟:它会安静地放过真问题 |

## 一、为什么需要它

> **为解决什么痛点而生**:2026-09-22 第一次认真整理这个库时,手工统计出来的数字是 —— **断链 13 处、`related` 双链失效 29 处、孤篇 20 篇、元数据违规 25 处、markdownlint 8677 条**。这些全是"不打开每一篇、不逐个点链接就看不见"的问题。库小的时候靠记性,长到一百多篇之后,唯一可靠的办法是让机器每次都能重算一遍。

**一句话定义**:巡检器是把"库的结构约定"翻译成可执行判据的一组脚本,跑一次就重算全库的结构健康度,并以退出码表达结论。

**大白话注解**:像体检报告。它不判断你身体好不好(内容对不对、写得好不好),只量血压血糖(链接通不通、有没有人引用、元数据齐不齐),哪项超标就把那一项和数值指给你。

## 二、怎么用

### 2.1 三条常用命令

```bash
cd "F:/0-Note/50-资源/工具/vault-check"

# 全量检查(列明细:每条问题都带 文件:行号 原因)
PYTHONIOENCODING=utf-8 python -B check_vault.py

# 只看汇总(改完东西先扫一眼)
PYTHONIOENCODING=utf-8 python -B check_vault.py --quiet

# 注:旧 MOC 口径的 --coverage / --moc-stats 两个开关已随 00-索引/ 目录删除(2026-09-25 收尾轮)
# 一起移除;要看覆盖率就读各项目 00-索引.md 顶部的统计行(由 A9 守着与实物一致)。
```

- `PYTHONIOENCODING=utf-8` **不是可选项**:Windows 默认 GBK,输出里的中文与文件名会直接把脚本顶崩(报 `UnicodeDecodeError` / 乱码)。
- `python -B` 只是不生成 `__pycache__`,保持目录干净。
- 想要机器可读结果给别的脚本吃,加 `--json`。

### 2.2 输出怎么读

```text
[A1 断链] 2 处
   10-项目/2026-掌握西班牙语B2/20-知识/词族.md:327 ../../../08-外语/西班牙语/2-词汇/不规则动词.md
[A4 项目索引覆盖] 1 处
   10-项目/2026-11-掌握Git/20-知识/Git.md:0 未在项目索引出现
结论:FAIL
```

- 第一行是**分类汇总**:`[检查项] 命中数`
- 下面每行是**一条问题**:`文件:行号 详情`(行号 `0` 表示"整篇级"问题,如缺 frontmatter、未登记)
- 最后一行是**结论**:全 0 就是 `PASS`

### 2.3 退出码(能接进自动化)

| 退出码 | 含义 |
| --- | --- |
| `0` | 全部检查通过(`PASS`) |
| `1` | 至少一项有问题(`FAIL`),明细已打印 |

所以它可以直接串进脚本:`check_vault.py --quiet || echo "库里还有问题"`。

### 2.4 什么时候跑

| 时机 | 理由 |
| --- | --- |
| **改完一批笔记/链接后** | 立刻知道有没有手抖断链 |
| **搬迁、改名、重排目录之后** | 这类操作最容易留下"看着对、其实解析不了"的链接 |
| **改完索引页之后** | A9 会核对统计行与实物是否一致,A14 会核对链接数 |
| **写新笔记之后** | A4/A6 会提醒你登记进项目索引页、补 frontmatter;`10-项目` 里的知识笔记还须写明来源项目(A13) |
| 提交前(理想习惯) | 它检查的都是"提交后很难再发现的静默损坏" |

## 三、它查什么:A1~A14 速查表

| 编号 | 查什么 | 判据要点 | 常见修法 |
| --- | --- | --- | --- |
| **A1** 断链 | 相对路径链接的目标是否存在 | 跳过 `http`/`#`/`mailto`;模板占位与语法示例走白名单;代码块与行内代码先被抹白再扫 | 改路径、或补建目标文件 |
| **A2** 双链失效 | `[[名]]` / `[[目录/名]]` 能否解析到真实文件 | 裸名按**文件名**命中,带路径的按**路径后缀**命中(库里有 18 个同名 `!项目说明.md`,裸名折叠会误判) | 改成正确文件名,或补路径消歧 |
| **A3** 孤篇 | 全库没有任何入链的笔记 | 裸双链只在**该名全库唯一**时才算入链,否则同名折叠会给所有同名文件"发入链"、掩盖真孤篇 | 在项目索引页或项目说明里登记一行链接 |
| **A4** 项目索引覆盖 | `10-项目/<项目>/20-知识/` 的每篇必须出现在该项目 `00-索引.md` 里(旧 MOC 口径 2026-09-25 随 MOC 删除退役) | `40-归档`(只进不出)与 `90-模板` 不扫;有 `20-知识` 却缺 `00-索引.md` 时另报「项目索引缺失」 | 在项目索引里加一行 |
| **A5/A6** 元数据 | 缺 frontmatter / `type` 非 8 种规范值 / `status` 非 4 种 / 字段数 > 8 | 豁免:根 `00-索引/00-索引.md`、`90-模板`、根 README、`10-项目/!问题追踪` | 按 README 的 schema 补齐或改值 |
| **A7** 路线一致性 | 根 `00-索引/00-索引.md` 的「计划与进度」与 `10-项目` **双向**一致,且项目 `status` 与产出相符 | 项目内除 `!项目说明.md` 与 `00-索引.md` 外还有 `.md` → `learning`,否则 `todo`(`!实施计划.md` 计入"有产出") | 补路线条目,或改 `status` |
| **A8** 标签规范 | 同一标签的大小写冲突(`windows` 与 `Windows` 并存) | 只报"同一小写形式在别处也出现过"的大写写法,不误伤 `Linux`/`RFID` 这类专名 | 统一成库内约定的小写 |
| **A9** 索引页统计 | 项目页统计行 `> 本项目知识 N 篇 · 状态 <status> · 覆盖 N/N(100%)` 与根索引汇总行 `> 全库知识 N 篇 · 项目 M 个` 必须与实物一致;统计行须落在文件前 8 行 | 只有项目页与根索引两种口径;旧 MOC 统计块与 `--coverage` / `--moc-stats` 开关已在 2026-09-25 收尾轮删除 | 按实物改写统计行;索引页 frontmatter 只留 `type` / `status` 才压得进 8 行 |
| **A10** 知识归属 | `10-项目` 里的成品知识是否住进了项目/容器的 `20-知识/` | 只有路径形如 `10-项目/<某个目录>/20-知识/…` 才算合规(裸 `10-项目/20-知识/` 没有归属,照报);只查 `type` 为 `algorithm`/`language`/`system`/`concept`/`tutorial` 的(`project`/`note`/`log` 放哪都合规) | 搬进**所属项目或容器**的 `20-知识/`(旧知识区已废除),或把 `type` 改成 `note`/`log` 表态 |
| **A11** 教学工作区 | 每个学习项目是否有 `teach` 状态层 | 有 `!项目说明.md` 的项目目录必须有 `MISSION.md` + `RESOURCES.md`,且**不能是空壳**(MISSION 要有 Why / Success / Constraints / Out of scope 四节,RESOURCES 要有 Knowledge / Gaps) | 按 `MISSION-FORMAT` / `RESOURCES-FORMAT` 补齐 |
| **A12** 归档判据 | `40-归档/` 下的项目必须在根 `00-索引/00-索引.md` 留一行登记(反向);「可归档」另走提示通道 | 归档物从入口消失就成了找不回来的死文件;根索引本身缺失时只发一条归因错 | 在根索引补一行,或把误放归档的知识归位到项目 `20-知识/` |
| **A13** 双向链接 | 项目 `20-知识/**/*.md` 每篇必须声明自己的来源项目 | 两种写法满足其一:`related` 里指向本项目 `!项目说明.md` 的链接,或**首段前 3 行的行首**写「来源:本项目」;两个容器与没有 `!项目说明.md` 的目录豁免 | 补 `related`,或首段首行加声明 |
| **A14** 索引页一致性 | 根索引必须逐行列全 `10-项目/` 的每个子目录;项目索引里指向本项目 `20-知识/` 现存 .md 的**链接数**必须等于实物数 | 容器与 `!问题追踪` 也要有行;缺索引/未登记/统计行分别归 A4/A4/A9,本检查不重复报;根索引未创建时跳过并只给提示 | 补行;把“只写了名字”的条目改成真链接,去掉重复登记 |

### 4.2 三个关键机制

**① 仓库根靠脚本位置反推**
`VAULT_ROOT = Path(__file__).resolve().parents[3]` —— 脚本在 `<仓库根>/50-资源/工具/vault-check/`,往上三层就是仓库根。所以整个工具**可以随库移动**,不需要改任何配置。

**② 先把代码"抹白"再扫链接**
`strip_code()` 把围栏代码块与行内代码**替换成等长空白**。这一步解决两个问题:代码里的 `[文字](网址)` 示例不会被当成真链接;同时**保持行号与列位置**,所以报错行号永远准确(如果直接删掉代码行,后面所有行号都会错位)。

**③ 白名单只写"故意为之"的东西**

- 链接白名单:模板占位路径、README 里的语法示例
- 双链白名单:刻意保留的「待补坑」,如 `[[快速排序]]`(留着提醒自己以后写)
- 豁免区:根 `00-索引/00-索引.md`/`40-归档`/`90-模板` 允许孤立;根 `00-索引/00-索引.md`/`90-模板`/根 README/`!问题追踪` 不要求 frontmatter
- 根索引**住在 `00-索引/` 目录里**(2026-09-25 起):Windows 资源管理器永远把文件夹排在文件之前且无法更改,所以把入口做成以 `00-` 开头的目录里的文件,它才在默认视图里排得到 `10-项目` 前面。检查器不关心它在哪 —— 只看 `vault_lib.ROOT_INDEX` 这一个常量,其余取根索引的地方全走它
- A13 的豁免只免「反向声明」:两个容器(`!名词解释` / `!系统与工具`)没有时间盒、指不出「本项目」;`20-知识/` 所在目录连 `!项目说明.md` 都没有的(如 `!问题追踪`)同理
- 提示通道:A12 的「可归档」与 A14 的「根索引未创建」打印在独立小节,**不进 FAIL 计数、不影响退出码** —— 只有真错误才让 `rc=1`
- 教学工作区协议文件(`MISSION.md`/`RESOURCES.md`/`NOTES.md`/`GLOSSARY.md` 与 `lessons/`/`reference/`/`assets/`/`learning-records/`)整体豁免 A3 与 A5-A6,也不计入 A7 的「项目产出」—— 它们是技能状态,不是库内笔记,由 A11 单独守

### 4.3 自检:检查器也要被检查

```bash
cd "F:/0-Note/50-资源/工具/vault-check"
for f in selftest_*.py; do PYTHONIOENCODING=utf-8 python -B "$f" | tail -1; done

# 分项预期(14 个文件,合计 107 用例):
# selftest_lib 7 / check 3 / extra 8 / a4 3 / teach 5 / archive 13
# backlink 13 / backlink2 9 / index 7 / index2 8 / project 12 / project2 8
# entry 2 / new_project 9
```

自检在**临时目录里造一个假库**,然后验证两类事:该报的报了(如放一个 `type: language` 的文件进 `10-项目` 根,A10 必须命中)、不该报的没报(如两个容器里的知识不要求写「来源:本项目」,A13 必须不报)。**没有自检的检查器比没有检查器更危险** —— 它会给你一个虚假的"全绿"。

## 六、边界:它查不到什么

| 查不到 | 原因 / 现状 |
| --- | --- |
| **内容对不对** | 只做结构检查;事实错误、逻辑错误、错别字(如 `palabas` 应为 `palabras`)它不知道 |

## 七、给维护者:怎么加一条新检查

1. 新开一个 `checks_<主题>.py`(或放进已有的同主题文件),写 `check_xxx() -> list[Finding]`;公共能力放 `vault_lib.py`。已经顶格的文件(`checks_project.py` 199、`new_project.py` 199)以及逼近上限的 `selftest_backlink.py` 198 / `selftest_index2.py` 197 都先拆再加
2. 在 `check_vault.py` 的 `groups` 列表里挂上,命名沿用 `A<n> 中文名`(这是 14 道检查的单一清单)
3. 在对应的自检文件补**两个**用例:会命中、不会误报(A1~A6 → `selftest_check.py` / `selftest_lib.py`;A4 → `selftest_a4.py`;A7 与项目口径 → `selftest_project*.py`;A8~A10 → `selftest_extra.py`;A11 → `selftest_teach.py`;A12 → `selftest_archive.py`;A13 → `selftest_backlink*.py`;A14 与索引分工 → `selftest_index*.py`;入口/提示通道 → `selftest_entry.py`)
4. 同步更新 README 双语、本笔记的速查表与文件表
5. 守住 200 行上限(超了就按主题拆文件,像 A8~A10 与 A12~A14 那样)
6. 跑一遍全库确认新检查在真实库上为 0(否则说明规则与现状不一致,得先决定改规则还是改库)
7. 跑 markdownlint 时给每个路径加 `:` 前缀(强制字面量,避开括号被当 extglob),并**打印被扫文件数**与 `git ls-files '*.md' | wc -l` 对齐 —— 只看 `0 issues` 会被静默漏扫骗过

**判据设计经验**:宁可"只报确定的问题"也不要"报一堆疑似"。例如 A8 只报**同一小写形式在别处也出现过**的大写标签,所以 `Linux`、`RFID` 这类只有一种写法的专名不会被误伤 —— 一个爱误报的检查器,很快就会被所有人忽略。
