## 四、工作流与硬规矩

### 协作规则(用户 2026-09-22 定,本项目始终遵守)

- **给上游发任何回复前,先把内容翻译成中文在对话里展示,等用户确认后再提交**(PR 评论、issue 评论、PR 描述都是如此)。原文仍用英文提交,中文只用于让用户审阅。
- **回复草稿要过反 AI 腔**:短句、直接说事、不堆小标题与加粗标签、不用"值得一提的是/如果你想"这类垫话;用户 2026-09-22 要求"AI 率小于 5%"。像人在 PR 下随手回的几句话,不像报告。

### 其余硬规矩

- 环境:Python 3.12+;west 仓库带 `uv.lock`,本地检查统一走 `poe`
- 提交:`git commit --signoff`(**DCO 是硬要求**)
- 分支与 PR:fork → 基于 `upstream/main` 开分支 → PR
- **Zephyr git 工作流与常见 GitHub 流程不同:每个 commit 自包含;更新 PR 用 amend/rebase + force-push,禁止 fixup / merge commit**
- 一次只推进一个 PR;上一版 review 未回复不新开 PR
- PR 描述必须写清三件事:解决哪个 issue、设计选择与理由、**本地怎么验证的**

## 五、风险与对策

| 风险 | 对策 |
|------|------|
| PR 提交后无人 review(开源最常见死法) | 优先选近期有 maintainer 活动的 issue;PR 描述写清验证步骤降低 review 成本;必要时在 Discord `#west` 礼貌催一次 |
| 重构 PR 被要求"不要动行为"而反复返工 | 硬约束:纯重构、行为零变化;先跑基线测试再动手 |
| 类型检查(mypy)不过 | 这个 issue 本质就是类型问题;先单跑 `poe types` 再跑 `poe all` |
| 贪多,同时开多个 PR | 硬约束:一次一个,合并或关闭后再开下一个 |
| 情绪受挫(被拒 / 被要求重写) | 被拒也算完成一个任务,但必须写清技术原因;review 往返本身就是面试素材 |

## 决策记录(为什么不那样做)

- **不选 Home Assistant 文档仓**(9,834 star / 6,386 贡献者,Markdown 即可贡献):技术深度最低、离嵌入式最远、面试可讲性最弱。
- **不选 ESPHome 主仓**(11,713 star / 1,392 贡献者):主仓测试多依赖编译(platformio),Windows 上跑测试吃力。
- **不从 west `#942` 起步**(10 评论):讨论已僵持,新人插进去容易被拖住。
- **不与内核线合并成一个项目**:内核线需要 Linux 环境与硬件,这条线现在就能开工;两者共用礼仪但节奏独立。
- **不用双系统,改用手头已有的 WSL2(Ubuntu 26.04)**(2026-09-22 用户定):装系统成本高、还要动分区;WSL2 能跑文档构建与 Python 工具链,已实测可用。注意 WSL2 内核是微软的,**内核模块相关实验不能用它**——那部分等有硬件与真 Linux 再说。
