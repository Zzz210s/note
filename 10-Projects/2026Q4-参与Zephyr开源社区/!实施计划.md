# 2026Q4-参与Zephyr开源社区 · 实施计划

> **给执行者:** 本文件只定义"做什么、做到什么算成、产物放哪"。环境搭建、写码、提交、回复 review 由本人执行。
> **本项目 spec:** [项目说明](<!项目说明.md>)

**目标:** 在 Zephyr 生态留下至少 3 个被合并的贡献(≥1 代码/工具链 + ≥1 文档),并与 maintainer 产生真实 review 往返。

**架构:** 三条入口依次推进 —— west 官方 Python 工具链 → Zephyr 文档 → Zephyr 工具链/测试基础设施。一次只推进一个 PR,合并或关闭后再开下一个。

**约束(来自 spec,逐条适用):**

- star 数与徽章不作为指标
- 每个 commit 必须 `git commit --signoff`(DCO)
- 保持 Zephyr git 工作流:每个 commit 自包含;**更新 PR 用 amend/rebase + force-push,禁止 fixup / merge commit**
- 一次只推进一个 PR;上一版 review 未回复不新开 PR
- PR 描述必须写清:解决哪个 issue、设计选择与理由、本地怎么验证
- 输出禁 emoji

## 产出物

```
开源贡献/
  00-环境与流程.md      Python 环境、poe 命令、DCO 身份、fork 与分支约定

  02-zephyr-docs.md     补丁 2 的认领记录、文档改动、PR 链接
  03-toolchain.md       补丁 3 的问题来源与 PR 链接
  提交清单.md           所有 PR 链接 + 状态(open / 需改 / merged / 关闭原因)
```

### Task 1:环境与流程就绪(前置,不完成不得往下走)

**Files:**
- Create: `开源贡献/00-环境与流程.md`

**Interfaces:**
- Produces: 一个能跑通 west 全部本地检查的环境;一个合规的提交身份

- [ ] **Step 1:fork 并克隆自己的 fork**

```bash
# 先在 GitHub 上 fork zephyrproject-rtos/west,然后
git clone https://github.com/<你的账号>/west.git
cd west
```

- [ ] **Step 2:装环境并跑通四项本地检查**

west 仓库带 `uv.lock`,本地检查统一走 `poe`:

```bash
uv sync
uv run poe all      # = test + lint + format + types
```

判据:`test` / `lint` / `format` / `types` 四项全绿;本地跑不了的项要写明原因(例如 Windows 上的平台差异)。

- [ ] **Step 3:配置 DCO 身份与 upstream**

```bash
git config user.name "<真实姓名>"
git config user.email "<有效邮箱>"
git remote add upstream https://github.com/zephyrproject-rtos/west.git
git fetch upstream
git checkout -b <描述性分支名> upstream/main
```

判据:`git log -1 --format='%an <%ae>'` 显示真实姓名与有效邮箱。

- [ ] **Step 4:把流程写进产物**

`00-环境与流程.md` 必须包含:poe 四个命令各自干什么、DCO 签名方式、amend + force-push 的更新方式、一次一个 PR 的纪律、`uv run` 与 `poe` 的关系。

### Task 2:补丁 1 —— west `#959`(`WestCommandsType` 提升为类)

**Files:**
- Modify(west 仓库):`src/west/manifest.py`
- Test(west 仓库):`tests/` 下与 manifest / extension commands 相关的测试文件
- Create: `开源贡献/01-west-959.md`

**Interfaces:**
- Consumes: Task 1 的环境
- Produces: 第一个被合并的代码贡献 + 一条可复用的 PR 流程

**issue 原文给出的设计约束(照抄自 issue `#959`,不要自创别的语义):**

- `_west_commands_list` 像构造函数
- `_west_commands_maybe_delist` 像字符串表示(即 `__str__` 类语义)
- `_west_commands_merge` 适合做成 `__iadd__`
- `_west_commands_manifest_dirs` 也要纳入类里
- issue 明确提示:**继承 `dict` 可能是最合适的做法**

- [ ] **Step 1:读原始讨论,确认改动范围**

先读 issue `#959` 与它引用的 PR `#920` 的那条 review 讨论,把"为什么当时没做"和"现在期望做成什么样"写进 `01-west-959.md`。**没有这一步不写代码。**

- [ ] **Step 2:读现状,列出所有使用点**

```bash
grep -rn "WestCommandsType" src/ tests/
grep -rn "_west_commands_" src/ tests/
```

判据:所有定义处与使用处都列进产物,并标出哪些要跟着改。

- [ ] **Step 3:先跑基线测试**

```bash
uv run poe test
```

判据:基线全绿(否则先记录基线失败项,不在此 PR 里修)。

- [ ] **Step 4:实现类(按 issue 给的四条语义)**

约束:① 继承 `dict`;② 提供构造语义、`__str__`、`__iadd__`;③ 纳入 `_west_commands_manifest_dirs`;④ **不改外部行为** —— 这是重构 PR,任何行为变化都会被 review 打回。

- [ ] **Step 5:本地四项检查全绿**

```bash
uv run poe all
```

判据:`test` / `lint` / `format` / `types` 全绿。类型检查尤其重要 —— 这个 issue 本身就是类型表达问题。

- [ ] **Step 6:补测试**

判据:新增或修改的测试覆盖新类的三条语义(构造、字符串表示、`+=` 合并);`poe test` 仍全绿。

- [ ] **Step 7:提交并推送到自己的 fork**

```bash
git add -A
git commit --signoff -m "manifest: promote WestCommandsType to a dict subclass"
git push -u origin <分支名>
```

commit message 规则:`area: 一句话`;一个 commit 只做一件逻辑改动。

- [ ] **Step 8:开 PR,描述里写清三件事**

① 解决哪个 issue(引用 `#959`);② 设计选择与理由(为什么用 dict 子类、三条语义怎么落);③ 本地验证步骤(贴 `poe all` 的结论)。

- [ ] **Step 9:回应 review(这一环比写码重要)**

规则:每条意见都回复;同意就改并 force-push;不同意就**给技术理由**,不沉默也不照单全收。每次往返记进 `01-west-959.md`。

- [ ] **Step 10:判据**

① PR 已提交且 CI 通过;② 至少 1 次 review 往返并已回复;③ 状态(merged / 需改 / 被拒并说明原因)写进 `提交清单.md`。**被拒也算完成本任务**,但必须写清技术原因。

## 风险与对策

| 风险 | 对策 |
|------|------|
| PR 提交后无人 review(开源最常见死法) | 优先选近期有 maintainer 活动的 issue;PR 描述写清验证步骤;必要时在 Discord `#west` 礼貌催一次 |
| 重构 PR 被要求"不要动行为"而反复返工 | 硬约束:纯重构、行为零变化;先跑基线测试再动手 |
| 类型检查(myypy)不过 | 先单跑 `poe types`,再跑 `poe all` |
| 贪多,同时开多个 PR | 硬约束:一次一个,合并或关闭后再开下一个 |
| Windows 与 CI 环境差异导致"本地绿、CI 红" | 记录差异;west 官方明确说"本地复现不了的 CI 失败算 bug",可以在 PR 里如实说明 |
